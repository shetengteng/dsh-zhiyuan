- **目标**：在不改变 DSH 插件运行时契约的前提下，让文件命名、目录组织和导出符号更接近 Java "一文件一类" 的心智模型，提升可读性与可维护性
- **非目标**：不修改 RPC channel、endpoint、`op` 值、工具名、命令名等已发布契约；不引入新抽象层；不为凑行数机械拆分小文件

## 1. 现状评估

当前仓库已经具备清晰的分层骨架：`controller/{command,tool,rpc}`、`service/{kb,search}`、`repository/kb`、`model/{entity,value,request,response,context,wire,error}`、`platform`、`content`、`view`。所有源文件都在 300 行以内，符合项目规则。

真正影响"一眼看懂"的不是缺类，而是以下几类隐性问题：

1. **文件名 ≠ 内容**：部分文件叫 `index.ts`、`types.ts`、`constants.ts` 这种泛化名字，实际承载具体实现或混合职责。
2. **死代码残留**：重构过程中遗留的旧实现未被清理，造成"同一个函数有两个版本"的认知负担。
3. **同类异名**：两套几乎相同的字段收窄函数分别挂在 Tool/RPC 下，命名风格不一致。
4. **View 组件聚合过粗**：一个文件塞多个组件，且共享原语混在业务弹框里。
5. **跨域常量杂烩**：包元信息、UI 标签、search/csv/table 限额、格式化函数挤在同一文件。

这些问题不会导致运行时错误，但会让新人或 AI 助手在定位代码时反复试错，也违背了"看到文件名就知道里面是什么"的工程直觉。

## 2. 设计原则

本方案的取舍基于以下四条原则，按优先级排序：

1. **契约不变**：RPC wire 字段、工具 schema、命令 flag、DSH slot 名称是对外契约，不在本轮调整范围。
2. **一名一类**：每个 `.ts/.tsx` 文件只承载一个主要职责（一个 class、一个工厂函数、一组强相关的纯函数）。文件名 = 主导出物名（PascalCase 组件用 PascalCase 文件名，kebab-case 模块用 kebab-case 文件名）。
3. **避免泛化门面**：不再新建 `utils.ts`、`helpers.ts`、`types.ts`、`constants.ts`、`index.ts`（除非它只是 barrel re-export）。
4. **渐进迁移**：每一步都可独立验证（`npm test && npm run build`），不做大爆炸重构。

## 4. 逐项变更说明

### 4.1 删除死代码

| 删除对象 | 理由 |
|---|---|
| `src/service/search/render-search.ts` | 整文件无人引用；`result/templates/index.ts` 的 `renderSearchResult` 才是 [kb-tool-controller.ts](file:///Users/stt/thinking/dsh-zhiyuan/src/controller/tool/kb-tool-controller.ts#L6) 使用的版本 |
| `src/service/search/search-groups.ts` | 整文件无人引用；`groupMatchesByFile`、`canMergeWindows`、`FileMatchGroup` 与 `file-summary.ts` 重复 |
| `result/templates/index.ts` 中的 `presentationMeta` 函数 | 工具注册使用的是 `searchPresentationMeta`，该函数无任何调用方 |

**好处**：消除"同一功能两个实现"的认知歧义；减少后续维护时的误改风险。

### 4.2 合并检索入口

将 `service/search/index.ts`（96 行编排逻辑）与 `service/search/knowledge-search.ts`（13 行透传壳）合并为 `search-kb.ts`。

**理由**：
- `index.ts` 作为实现文件违反"一名一类"原则，且与 barrel 语义冲突。
- `knowledge-search.ts` 仅透传同名函数 `searchKb`，增加一层无意义的间接调用。
- 合并后文件名 `search-kb.ts` 与主导出函数 `searchKb` 直接对应。

**好处**：调用链缩短一层；文件名即函数名，IDE 跳转直达实现。

### 4.3 导入用例：收敛为 `service/kb/import/` 包并按角色命名

#### 4.3.1 现状与问题

导入相关代码分散在 `service/kb/` 下的 7 个 `import-*` 文件中。调用链本身是清晰的单一用例：

```text
enqueueKnowledgeImport（import-service.ts，任务排队）
  ├─ importDroppedBytes（import-drop.ts，浏览器拖入字节 → 临时文件）
  │    └─ importFiles（import.ts，主编排）
  ├─ importFiles
  │    ├─ walkSource / existingHashes / dirSize      （import-read.ts，读：来源展开 + 库内快照）
  │    ├─ contentRegistry.prepareImport              （content/，按格式转换）
  │    ├─ ingestPrepared                             （import-write.ts，写：配额→去重→越界→原子落盘）
  │    ├─ uniqueName / relativeSourcePath / ...      （import-check.ts，命名与路径规则）
  │    └─ rememberLastDestinationCategory            （import-destination.ts，最近类目记忆）
```

映射到 Java 是"1 个 Service + 6 个协作者组件"的标准形状。当前不达标的不是拆分本身，而是三个命名问题：

1. **`import-service.ts` 抢走了本该属于主用例的名字**：真正的主编排（`importFiles`）反而住在与 JS 关键字撞名的 `import.ts` 里。
2. **文件名角色信息为零**：`read`/`write`/`check` 是含糊动词。`import-check.ts` 实际内容是 `uniqueName`、`relativeSourcePath` 等纯命名规则，根本不"check"。
3. **`import-` 前缀重复 7 次**：字母序归组靠前缀表达，而目录本身就能表达归属。

#### 4.3.2 拆分保留的理由

| 约束 | 说明 |
|---|---|
| 300 行上限 | 合成一个文件将超过 400 行，违反项目规则 |
| 可测性 | `existingHashes`（全库 sha256）、`ingestPrepared`（安全校验）、`enqueueKnowledgeImport`（任务态）各自有独立测试夹具，需要能单独打桩 |
| 协作者契约 | TS 模块即"final class + static 方法"，按协作者拆分等价于 Java 的 `ImportService + ImportSourceScanner + ImportEntryWriter + ImportNamingPolicy + ImportDestinationResolver` 组合 |

#### 4.3.3 目标结构

```text
src/service/kb/import/
├── import-service.ts          # importFiles 主编排（原 import.ts）
├── import-job.ts              # enqueueKnowledgeImport（原 import-service.ts）
├── import-source-scan.ts      # walkSource / existingHashes / dirSize（原 import-read.ts）
├── import-entry-writer.ts     # ingestPrepared（原 import-write.ts）
├── import-naming.ts           # uniqueName / relativeSourcePath / outputRelativePath（原 import-check.ts）
├── import-destination.ts      # resolveImportDestination / rememberLastDestinationCategory（不变）
└── dropped-bytes-import.ts    # importDroppedBytes（原 import-drop.ts）
```

命名规则：**目录承载"导入"语义，文件名只写角色**。`service` 回归主编排、`job` 表达任务提交、`source-scan` / `entry-writer` 是协作类名词、`naming` 表达无状态规则。

#### 4.3.4 顺手修复

- `ingestOne` 将 9 字段 `args` 整包传给 `ingestPrepared`，后者只用 6 个字段。迁移时把参数包按协作者真实契约收窄，避免两处类型靠注释对齐。
- `import-check.ts` 中 `looksBareName`、`missingSourceMessage` 属于"错误文案与判定"，与命名规则同文件但职责不同；随迁移并入 `import-naming.ts` 顶部注释标明分区，或按行数发展独立成 `import-source-errors.ts`。

### 4.4 抽取共享字段收窄原语

新建 `platform/field-reader.ts`，统一 `asRecord`、`requireString`、`optionalString`、`optionalBoolean`、`optionalPositiveInteger` 等基础收窄函数。

`kb-tool-request-mapper.ts` 和 `knowledge-request-codec.ts` 改为 import 共享原语，各自只保留渠道差异的 build 逻辑。

**理由**：
- 当前两套函数逻辑几乎一致，但命名风格不同（`requireToolString` vs `requireString`），属于"同类异名"反模式。
- Java 中这类行为会放在一个 `FieldReader` 工具类里，TS 等价于一个纯函数模块。
- `Tool` 前缀把"类行为"摊平进每个函数名，正是 Java 社区反对的命名方式。

**好处**：单一真相源；新增渠道只需写 mapper，不必复制收窄逻辑；命名一致降低心智负担。

### 4.5 Context 与常量拆分

| 现位置 | 新位置 | 理由 |
|---|---|---|
| `model/context/kb-context.ts` 中的 `DestinationResolution` | `model/context/import-context.ts` | 它是导入目的地解析产物，与 catalog 事务上下文无关 |
| `model/context/search-pagination-context.ts` | `model/context/search-cursor.ts` | 内容是游标载荷与查询类型，不是"分页上下文"；改名后与 `pagination.ts` 的编解码职责区分更清晰 |
| `model/constants.ts` 中的 `SEARCH_*` | `model/search-limits.ts` | 按域归类，避免单文件膨胀 |
| `model/constants.ts` 中的 `CSV_*` | `model/csv-limits.ts` | 同上 |
| `model/constants.ts` 中的包元信息 | `model/package-info.ts` | 包名、版本、DSH 目标版本是部署级常量，与业务限额不同域 |
| `model/constants.ts` 中的 `formatKbDisplayTitle` | `model/display-formatters.ts` | 函数不应住在 constants 文件里 |
| `model/constants.ts` 中的 UI 标签/命令名 | 保留在原文件或移入 `package-info.ts` | 这些是插件身份标识，与包元信息同域 |

**好处**：每个文件只表达一个领域的约束；新增限额时不用在 46 行大杂烩里找位置。

### 4.6 View 组件拆分

#### 4.6.1 `dialogs/KbDialogs.tsx` → 多文件

当前文件导出 5 个组件，其中 `Field` 和 `Note` 是被 `ImportDialogs`、`PrefsPage`、`PreviewDialog`、`SearchDialog` 共用的表单原语，却住在"Kb 弹框"文件里——这违反了"一文件一类"和"共享原语独立"两条原则。

拆分方案：

| 新文件 | 内容 |
|---|---|
| `dialogs/DialogField.tsx` | `Field` + `Note`（通用表单原语） |
| `dialogs/CreateKbDialog.tsx` | `CreateDialog` |
| `dialogs/EditKbDialog.tsx` | `EditDialog` |
| `dialogs/ConfirmDialog.tsx` | `ConfirmDialog` |
| `dialogs/KbDialogs.tsx` | 删除（或保留为 barrel re-export，过渡期后可删） |

**好处**：每个弹框文件自包含；共享原语有明确归属；新增弹框时不会继续往 KbDialogs 里堆。

#### 4.6.2 `drop-source-path.ts` → 两文件

当前 128 行 11 个导出，混了三类职责：DataTransfer 拖拽判定、落点路径解析、文件转 base64。

拆分方案：

| 新文件 | 内容 |
|---|---|
| `drag-utils.ts` | `listDragTypes`、`isFileDrag`、`claimFileDrag`、`droppedFile`、`isDroppedDirectory` |
| `drop-source.ts` | `DroppedSource`、`sourceDisplayName`、`droppedSourcePath`、`resolveDroppedSource`、`fileToBase64` |

**好处**：拖拽判定是纯 DOM API 封装，与业务路径解析解耦；未来若换用 File System Access API 只需改 `drop-source.ts`。

#### 4.6.3 `view/types.ts` → `view/view-models.ts`

该文件被 20+ 文件引用，是事实上的 View 类型门面。分层文档 §5.5 明确反对长期 facade，但 Client 侧确实需要一个聚合 View 专用类型的出口（避免每个组件写一长串 `../../model/response/...`）。

折中方案：改名为 `view-models.ts`，明确表达"这是 View 层的模型投影集合"，并在文件头注释标注"仅 re-export model 类型 + View 自有类型（如 DialogKind）"。

**好处**：名字传达意图；后续若需拆分，调用方搜索 `view-models` 比搜索 `types` 更容易定位。

#### 4.6.4 `Icons.tsx` + `SectionIcon.tsx` → 合并

两个文件都在 `settings/` 下，都是 SVG 图标。合并为一个 `Icons.tsx`，`SectionIcon` 及其 path 常量迁入。

**好处**：图标集中管理；新增图标时只有一个文件要改。

### 4.7 Skills 目录重命名

`skills/skill.ts` → `skills/zhiyuan-skill.ts`。

**理由**：`skills/skill.ts` 路径冗余（目录名已表达复数），且无法从文件名看出是哪个 skill。改名后与导出符号 `ZHIYUAN_SKILL` 对应。

### 4.8 不动的部分

| 对象 | 理由 |
|---|---|
| `model/entity/catalog.ts` 含 `Catalog` + `KbCard` | 聚合根惯例，KbCard 是 Catalog 内嵌实体，不应拆 |
| Wire 类型中的 `id` 字段 | RPC 契约，重命名会破坏协议 |
| `content/` 的 server/client/shared 分组 | 按格式内聚是设计文档明确要求 |
| `payload/*.ts` 的 parser 文件 | 每个文件对应一个 Response 类型，已符合一名一类 |
| `*-styles.ts` 样式文件 | CSS-in-JS 字符串常量，按组件分组合理 |

## 5. 预期收益

1. **可读性**：看到文件名就知道里面是什么，不需要打开文件确认。新人 onboarding 时间缩短。
2. **可维护性**：修改某个功能时，影响范围限定在命名明确的少数文件；不会出现"改了 A 发现 B 也有同名函数"的意外。
3. **AI 协作效率**：LLM 在定位代码时依赖文件名语义；泛化名字会导致多次试错检索。明确命名直接降低 token 消耗。
4. **与 Java/Spring Boot 心智对齐**：团队成员若有 Java 背景，无需重新学习"这个项目的 index.ts 其实是实现文件"这类隐式约定。
5. **合规性**：继续满足 300 行限制；不引入新抽象层；不破坏既有契约。

## 6. 最近实践参考

本方案的取舍参考了以下近期工程实践：

1. **Spring Boot 3.x 的包结构约定**：Controller/Service/Repository 按职责分包，DTO 按 Request/Response/Entity 分目录，而非按技术层（如 `dto/`、`vo/`）大包揽。本仓库的 `model/{request,response,entity,value,context,wire,error}` 已对齐此思路，本次只是把同样的纪律应用到文件名层面。
2. **TypeScript 社区的 "barrel tax" 反思**：2024–2025 年多篇实践文章指出过度使用 `index.ts` barrel 会导致 tree-shaking 失效和 IDE 性能下降。本方案将实现型 `index.ts` 改为具名文件，仅保留纯 re-export barrel。
3. **React 组件文件组织趋势**：Next.js App Router 和 shadcn/ui 等项目推荐"一组件一文件 + 同目录 colocate hooks/styles"。本方案的 View 拆分与此一致。
4. **DDD 战术设计的 TS 落地**：Eric Evans 的 Entity/Value Object/Context 分类在 TS 项目中常被简化为目录约定。本方案保留了分层文档已确立的分类，仅在文件名上强化语义。
5. **DSH 插件自身的迭代经验**：前几轮重构（catalog v1→v2、bases→kbs、search cursor v4）证明"先冻结契约再动内部结构"的节奏可行；本次延续同一策略，不动 wire 字段。
