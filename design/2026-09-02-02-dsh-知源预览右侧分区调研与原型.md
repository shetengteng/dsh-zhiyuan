# 知源预览右侧分区：DSH 能力调研与 ASCII 原型

> 状态：调研完成，方案 B 已落地；长期建议仍是推动 DSH 提供专用预览接缝
>
> 日期：2026-09-02
>
> 目标 DSH：`0.1.1-rc.2`

## 1. 结论先行

DSH 支持右侧详情栏，且它是三栏 `AppFrame` 的原生能力。布局包提供 `details` slot，布局服务提供 `ctx.layout.openDetails()` 与 `ctx.layout.closeDetails()`，详情栏默认关闭，打开后默认宽度为 360px，允许拖动调整到 300～520px。

但是，当前 DSH 的详情能力面向“一个已选中的工具调用”，不是面向工具结果里的“某一条命中片段”。知源当前注册的是 `tool.call.toolview`，卡片点击拿到的是本地组件状态里的 `SearchHit`，这个 slot 的 owner props 没有打开 DSH 详情栏、写入详情选择、传入自定义预览载荷的接口。

当前版本采用了方案 B：知源接管 `details` single slot，使用插件内 controller 保存当前 hit，再把：

```text
命中卡 -> controller.select(hit) -> ctx.layout.openDetails()
```

接到 DSH 原生右侧栏。右栏组件仍复用 `MdEditor(readonly)`，因此能保证展示刚点击的文件、行号和 Markdown 片段。

由于目标版本的 `ctx.layout` 只有开关接口，没有设置详情宽度的方法，知源在预览挂载期间通过一个隔离的兼容层把宿主第三列从默认 360px 放宽到 420px，并同步宿主拖拽手柄位置；预览释放时恢复宿主原有几何。窗口不足以保留 DSH 约 640px 的中间区域时，不强行放宽。

这个落地选择有明确边界：它会替换 DSH 原生 `DetailsPanel`，当前版本优先服务知源引用预览；后续仍建议 DSH 增加“详情预览载荷”接缝，让知源只提供内容渲染而不接管整栏。

## 2. 当前知源实现

当前搜索命中卡在 [`src/client/toolview/KbSearchView.tsx`](../src/client/toolview/KbSearchView.tsx) 注册为 `kb_search` 的 `tool.call.toolview`：

```text
搜索结果卡
  ├─ 数字引用标签 1
  ├─ 文件路径和行号
  └─ 命中行摘要
       └─ 点击后打开 DSH details 右栏中的 MdEditor(readonly)
```

预览通过 [`src/content/client-api.tsx`](../src/content/client-api.tsx) 分派到 Markdown 或 CSV 的格式专属组件，因此 Markdown 的代码块、标题和命中行高亮逻辑保持一致。命中选择由 [`src/client/toolview/preview/preview-state.ts`](../src/client/toolview/preview/preview-state.ts) 管理，右栏通过 [`src/client/toolview/preview/KbPreviewPanel.tsx`](../src/client/toolview/preview/KbPreviewPanel.tsx) 消费。

标签样式在 [`src/client/settings/styles.ts`](../src/client/settings/styles.ts) 中使用 DSH 的业务色 token，标签只显示数字，不显示方括号。数字本身仍然是语义信息，颜色不是唯一识别方式。

## 3. DSH 本地能力调研

本次调研读取了本机安装的 DSH `0.1.1-rc.2` 包、类型声明、中文 README 和浏览器 bundle，没有使用网络资料。

### 3.1 原生三栏和右侧 details 栏

`@deepseek-ai/dsh-client-ui-layout` 的中文 README 明确描述了三栏 `AppFrame`，并声明 `sidebar`、`conversation`、`details` 等 slot。布局类型声明中，`details` 是一个 session 作用域的 single slot，由会话包的 `DetailsPanel` 占用。

本地依据：

```text
<dsh-install>/0.1.1-rc.2/node_modules/
  @deepseek-ai/dsh-client-ui-layout/README.zh.md
  @deepseek-ai/dsh-client-ui-layout/lib/types/client/index.d.ts
  @deepseek-ai/dsh-client-ui-layout/lib/types/client/service.d.ts
```

布局服务声明了：

```ts
interface ILayout {
  openDetails(): void
  closeDetails(): void
}
```

布局实现还说明了这些行为：

- 详情栏关闭时宽度为 0，不会销毁整个布局壳。
- `openDetails()` 在关闭状态下使用默认宽度 360px。
- 详情栏宽度范围为 300～520px。
- 中间会话区域至少保留约 640px；窗口太窄时详情栏会收缩到 0。
- 没有当前的非空会话时，详情栏不显示。
- 切换会话时，详情栏会关闭。
- 面板几何是瞬时状态，不写入 `localStorage`。

知源的预览宽度适配位于 `src/client/toolview/preview/preview-width.ts`，只依赖 DSH 的三栏布局语义和 `data-side="details"` 手柄属性，不依赖构建产物中的哈希 class。未来 DSH 提供 `setDetailsWidth` 后，应移除这层兼容逻辑，改用公开接口。

这些约束很适合作为知源预览的外壳，不建议在插件里重新实现一套固定定位的“假右栏”。

### 3.2 原生详情面板能展示什么

`@deepseek-ai/dsh-client-ui-conversation` 的 `DetailsPanel` 会从共享 chat store 读取 `selection`，再通过 `callId` 找到一个工具调用。它的结构大致是：

```text
详情
  ├─ 工具名称
  ├─ Input
  │    └─ 工具参数 JSON
  └─ Output
       └─ conversation.details.tool slot
```

本地依据：

```text
<dsh-install>/0.1.1-rc.2/node_modules/
  @deepseek-ai/dsh-client-ui-conversation/lib/types/client/contract/views.d.ts
  @deepseek-ai/dsh-client-ui-conversation/lib/types/client/contract/slots.d.ts
  @deepseek-ai/dsh-client-ui-conversation/lib/types/client/skeleton/DetailsPanel.d.ts
  @deepseek-ai/dsh-client-ui-conversation/lib/client.js
```

`conversation.details.tool` 可以替换 Output 的具体渲染器，owner 会收到冻结的工具 `block` 和会话 `cwd`。这说明知源理论上可以让 `kb_search` 的 Output 渲染成 Markdown 预览，但这里仍然缺少“当前点击的是第几条 hit”这层选择信息。

### 3.3 DSH 的打开链路和当前限制

会话类型声明里已经有：

```ts
interface ChatViewInjected {
  openDetails(target: SelectionTarget): void
}
```

当前 DSH 的实现会先把 `SelectionTarget` 写入 chat store，再调用 `layout.openDetails()`。`SelectionTarget` 只包含 `turnSeq`、可选 `stepSeq`、`callId` 和 `toolName`，没有 `hit.n`、文件路径或 Markdown 预览正文。

更重要的是，当前 `0.1.1-rc.2` 的会话 README 把“详情面板没有入口”列为已知限制：`openDetails` 已实现，但组装后的工具行没有调用入口。对知源来说，现有 `tool.call.toolview` owner 只有：

```ts
{
  callId,
  toolName,
  block,
  cwd,
  home,
  openFile,
  inspect
}
```

没有 `openDetails` 或 `selectDetails`。知源当前通过 [`src/client/index.ts`](../src/client/index.ts) 注册这个 keyed slot，因此无法只在 `KbSearchView` 内取得会话 ChatView 的 `openDetails` 回调。

## 4. 能力矩阵

| 能力 | DSH 当前支持 | 对知源的影响 |
|---|---|---|
| 三栏 AppFrame | 支持 | 可以使用原生右侧列，不必自己模拟固定右栏 |
| 打开和关闭 details | 支持 `ctx.layout` | 只有布局开关，没有知源 hit 数据 |
| 选中工具调用 | 支持 `SelectionTarget` | 选择粒度是 call，不是单条搜索命中 |
| 自定义工具详情 Output | 支持 `conversation.details.tool` | 可以换 Output renderer，但拿不到点击的 hit |
| 自定义整个 details 栏 | 可以注册 `details` single slot | 会替换原生 DetailsPanel，影响所有工具详情 |
| 工具卡自定义 | 支持 `tool.call.toolview` | 当前知源已经使用，owner 没有 details 回调 |
| 任意插件预览右栏 | 没有专用 `preview` slot | 需要 DSH 扩展或接管 `details`；当前用兼容层调整到 420px |
| 任意助手句子中的 React tag | 没有 assistant prose renderer slot | 插件不能把模型最终句子的数字直接变成 React `span` |
| 只读 Markdown 组件 | 知源已有 `MdEditor` | 右栏可以复用，不需要再造 Markdown renderer |

## 5. ASCII 原型

### 5.1 推荐的桌面形态

下面的 `1` 是视觉标签里的数字，最终 UI 不显示方括号。ASCII 中的外框只是布局示意。

```text
+------------------+----------------------------------------------+--------------------------+
| 知源              | 对话                                         | 预览                     |
|                  |                                              |                          |
| 工作库            | 去年那个供应商合同的违约条款写了什么？       | 1  供应商合同.md         |
|  生活库           |                                              | 合同/2024                |
|                  | 命中卡                                       | 行 32                    |
|                  | +------------------------------------------+ |                          |
|                  | |  1   合同/2024/供应商合同.md:32-38       | | 关闭                     |
|                  | |      违约责任和赔偿方式...                | |                          |
|                  | +------------------------------------------+ | Markdown 只读预览        |
|                  |                                              | +----------------------+ |
|                  | 根据合同，违约方需要承担...  1               | | # 供应商合同         | |
|                  |                                              | |                      | |
|                  |                                              | | 第 32 行命中高亮     | |
|                  |                                              | |                      | |
|                  |                                              | | 正文、表格、代码块   | |
|                  |                                              | +----------------------+ |
|                  |                                              |                          |
+------------------+----------------------------------------------+--------------------------+
```

交互要点：

1. 点击命中卡后，中间对话不跳转，右侧栏打开并展示当前 hit。
2. 点击另一张命中卡，右侧栏原地切换文件、行号和 Markdown 内容。
3. 关闭按钮、Escape 和 DSH 原生详情栏关闭动作都只关闭右栏，不清空对话。
4. 右侧沿用 DSH 的拖动手柄和宽度约束。
5. `MdEditor` 保持 `readonly`，工具栏不提供编辑动作。

### 5.2 窄窗口回退

DSH 在可用宽度不足时会把 details 栏收缩到 0。知源需要保留当前 Modal 作为回退，避免窄窗口中点击卡片后没有预览。

```text
可用宽度不足

+------------------------------------------------------+
| 对话                                               × |
|                                                      |
| 命中卡                                               |
| +--------------------------------------------------+ |
| |  1  合同/2024/供应商合同.md                       | |
| |     违约责任和赔偿方式...                         | |
| +--------------------------------------------------+ |
|                                                      |
|        打开只读预览 Modal                           |
+------------------------------------------------------+
```

### 5.3 右栏内部信息层级

```text
+--------------------------+
| 供应商合同.md       1 ×  |
| 第 32–38 行 · 命中第 32 行 |
|--------------------------|
|                          |
| # 供应商合同             |
|                          |
| 第 32 行高亮              |
|                          |
| ...                      |
+--------------------------+
```

右栏的 Markdown 正文直接铺在面板内容区，不再套第二层卡片边框；滚动由右栏内容区统一承载，避免外层和编辑器内容区同时出现纵向滚动条。

ASCII 原型中的“第 32 行高亮”只是状态注释，不代表最终页面要显示额外文字。最终页面应继续使用编辑器已有的高亮样式。

## 6. 推荐实现路线

### 方案 A：新增 DSH 预览接缝，推荐

让 DSH 为工具行提供一个面向详情栏的选择接口，概念上类似：

```ts
openPreview({
  callId,
  title,
  kind: 'markdown',
  path,
  startLine,
  endLine,
  focusLine,
  text,
})
```

这是设计草案，不是当前 DSH 已存在的 API。数据应由 DSH 负责在当前 session 范围内传递，详情栏继续由 DSH 负责开关、宽度、响应式和关闭行为。知源只负责提供 `MdEditor(readonly)` 这一类预览内容。

优点：

- 不替换所有工具的原生 DetailsPanel。
- hit 选择是结构化数据，不依赖把路径、行号和正文拼进字符串后再解析。
- DSH 可以统一处理 session 切换、窗口变窄、Escape 和 panel width。
- 后续其他插件也能复用文件、Markdown 或 JSON 预览。

需要 DSH 明确的接口问题：

1. 预览载荷挂在 `SelectionTarget` 上，还是单独使用 preview store。
2. 详情栏如何区分 native tool detail 和 plugin preview。
3. 预览是否只保留内存态，是否允许回放历史工具结果。
4. `text` 的格式声明如何避免 Markdown 和普通纯文本混淆。

### 方案 B：知源接管 `details` slot

知源可以注册 DSH 的 `details` single slot，自己维护当前 `selectedHit`，点击卡片时调用 `ctx.layout.openDetails()`，右栏组件从知源 controller 读取预览信息。本次实现采用了这条路线；controller 随一次插件 apply 创建，右栏接收 session 标识，在切换 session 时清空旧正文。

这个方案在当前 DSH 上可行，但代价明显：

- 会替换 DSH 原生 DetailsPanel。
- 其他工具的 Input、Output、复制和详情展示需要知源重新兜底。
- 需要额外实现 session 切换、空态、窄窗口和详情关闭同步；本次已实现 session 清理、空态、Escape、关闭按钮和触发卡片焦点回归。
- 不能把原生 `DetailsPanel` 继续作为其他工具的兜底，因为当前 DSH 没有 additive details slot；其他工具的原生详情能力会暂时被知源右栏替换。

因此它适合作为当前 DSH 版本的可开发实现，但长期仍应回到方案 A。

### 方案 C：继续使用 Modal，作为兼容回退

方案 C 仍可作为兼容回退：DSH 旧版本没有 `layout` 或窗口让步后 details 不可见时，继续使用 Modal。当前目标版本已注入 `layout`，本次桌面实现优先使用右栏；窄窗口回退需要下一步接入可观察的实际 details 宽度后再启用，避免仅按 viewport 猜测。

长期建议仍是“方案 A + 方案 C”：宽窗口使用 DSH 原生右栏，窄窗口或 DSH 旧版本继续使用 Modal。

## 7. 安全与可访问性约束

- 引用数字来自已校验的 `SearchHit.n`，标签通过 React 子节点渲染，不向 HTML sink 写入拼接 HTML。
- 文件路径和正文仍作为文本传入预览组件，不使用 `dangerouslySetInnerHTML`。
- 标签同时显示数字和 `aria-label`，不能只靠淡蓝色区分引用。
- 淡蓝色使用 DSH 业务色 token 的低强度混合，兼容浅色和深色主题，不硬编码纯白或纯黑。
- 右栏必须有可见关闭按钮和键盘 Escape 行为，焦点关闭后回到触发卡片；本次已实现。
- 只读预览不能携带保存、写文件或编辑命令。
- 路径、行号、正文和 `focusLine` 在进入预览边界前继续走现有校验，不因为换成右栏而放宽。

## 8. 验收标准

右侧分区真正实现时，至少需要满足：

1. DSH 宽窗口下点击某条 hit 后，右栏显示同一条 hit，而不是默认显示第 1 条。
2. 卡片标签和答案文本都只显示数字，不出现 `[1]`。
3. 右栏复用 `MdEditor(readonly)`，Markdown 内容和当前弹框一致。
4. `focusLine` 对应正确的文件行，切换 hit 后不会沿用上一个 hit 的高亮位置。
5. 关闭右栏后仍能继续滚动和点击对话卡片。
6. 右栏宽度遵守 DSH 的 300～520px 约束；窄窗口回退 Modal 属于兼容回退待办。
7. 切换 session 后不会展示上一个 session 的文件正文。
8. 当前版本明确采用 `details` takeover，原生 DSH 工具详情暂不作为验收项；待 DSH 提供 additive preview 接缝后恢复该要求。
9. 浅色、深色主题下淡蓝标签均有足够文字和边界对比度。
10. `npm test`、`npm run build` 已通过；本机没有安装 `tsc`，`npx tsc --noEmit` 因网络不可用未完成；手动浏览器验收仍需在 DSH Web profile 中完成。
