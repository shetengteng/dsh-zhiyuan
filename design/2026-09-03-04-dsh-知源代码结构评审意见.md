## 3. P0：影响正确性 / 阻塞既定扩展路线

### 3.1 `catalog.json` 并发读改写竞争 + 非原子写入 ✅ 已修复

已落地：`withCatalogLock`/`withCatalogTx`（src/catalog.ts:102-124）实现进程内单写者；`writeCatalog` 改为临时文件 + rename 原子写（src/catalog.ts:126-137）；`createBase`/`updateBase`/`deleteBase`/`markUsed`/`rememberLastDest`/`setPrefs` 全部收敛到 `withCatalogTx`。

`readCatalog`/`writeCatalog` 是裸 read-modify-write（src/catalog.ts:71-86），且不经过 `JobRunner` 串行队列。当前至少有这些写入点可以并发交错：

- `searchBase` 每次搜索末尾 `markUsed` 写 catalog（src/search.ts:207）；
- `rememberLastDest`、`setPrefs`、`createBase`、`updateBase`、`deleteBase` 各自写 catalog。

典型竞争：`kb_search` 进行中用户在设置页 `setPrefs`，两边同时 read → 后写者覆盖前写者，丢失 `lastUsedAt` 或偏好。另外 `writeFile` 直接覆盖，进程在写入中途崩溃会留下截断的 `catalog.json`，下次 `parseCatalog` 静默丢弃 bases（卡片全丢）。

建议（改动小、收益大）：

1. `writeCatalog` 改为临时文件 + rename（复用 `writePreparedEntry` 的模式）；
2. 所有 catalog 写路径收敛到一个模块级互斥队列（不必动 JobRunner 的 op 语义，一个 `withCatalogLock(fn)` 即可），Host 进程内单写者。

### 3.2 `prepareImport` 单产物契约与 XLSX 路线冲突 ✅ 已修复

已落地：`prepareImport` 返回 `Promise<PreparedEntry[]>`（src/content/host-contract.ts:43），`ingestOne` 返回 `IngestFileResult[]` 并按产物遍历、逐产物累计配额（src/ingest.ts:177-242）。

`SourceFormatHandler.prepareImport` 返回单个 `PreparedEntry`（src/content/host-contract.ts:43），而 `2026-09-03-01` 方案明确「xlsx 以后导入会转换成**一个或多个** csv 条目」。当前 `ingestOne` 的去重、配额、改名、结果上报都按单文件展开，多产物格式接入时这整段都要返工。

建议现在就把契约扩为 `prepareImport: (...) => Promise<PreparedEntry[]>`（当前两个 handler 返回长度 1 的数组即可），`ingest.ts` 的循环体改为按产物遍历。等 xlsx 真进来再改，`IngestFileResult` 的语义（sourceRelPath ↔ 多个 relPath）会更难对齐。

### 3.3 CSV 专用方法泄漏进通用 `EntryFormatHandler` ❌ 未改（按 §9.6 与 xlsx 排期绑定）

复核：仍是 `readCsvEditorPage?`/`writeCsvPatch?` 挂在通用 handler 上，registry 用 `format !== EntryFormat.Csv` 特判（src/content/host-registry.ts:83-96）；Client 四处泄漏（`getCsvPatch`/`onLoadCsvPage`/`onSaveCsv`/`csv?`）均未收口。

`readCsvEditorPage` / `writeCsvPatch` 挂在通用 handler 上，registry 里用 `format !== EntryFormat.Csv` 特判（src/content/host-registry.ts:83-96）；`bases.ts` 也为此各开一个具名透传函数。下一个「可编辑表格类格式」（正是 xlsx 的目标形态）接入时，要么复制一份 `readXlsxEditorPage` 全链路，要么被迫改造契约。

建议：把这两个方法收敛成一个能力接口，例如 `tableEditor?: { readPage, writePatch }`，registry 按 `handler.tableEditor` 存在与否路由，`bases.ts` 合并回一个 `readTablePage`/`writeTablePatch`。Client 侧 `op: 'readCsvPage'` RPC 字段是持久契约，可以保留不动，只在 Host 内部改。

同一泄漏也在 Client 编排层，不只 Host handler：

| 位置 | 泄漏点 |
| --- | --- |
| `EntryEditorHandle` | `getCsvPatch?` |
| `EntryPreviewContentProps` | `onLoadCsvPage?` |
| `PreviewDialog` | `onSaveCsv` / `onLoadCsvPage` |
| `ReadEntryResult` | 可选字段 `csv?`（`format + csv?` 而不是判别联合） |

`tableEditor` 落地时，Client 这四个点必须一起收口；只改 Host 会留下 `getXlsxPatch` / `onLoadXlsxPage` / `ReadEntryResult.xlsx` 的下一轮复制。RPC `op` 名可继续叫 `readCsvPage` / `writeCsvPatch`。实施时机见 §7 第 6 步与 §9.6。

## 4. P1：性能与稳健性（库变大前必须处理）

### 4.1 全库重扫/全量哈希随规模线性退化 ❌ 未改

复核：`existingHashes`/`dirSize`/`countDocs`/`textDocumentBytes` 仍每次全量执行，manifest 缓存未建。

- `listBases` 对每个库 `countDocs`（递归走全库）+ `listBaseCategories`（src/bases.ts:78-94）。设置页每次 `refresh` 都触发 `op: 'list'`，10 库 × 千文件时 UI 会明显变慢。
- `ingest` 每次 `existingHashes`（对库内每个文件算 sha256）+ `dirSize`（src/ingest.ts:31-49, 111-112）。导入 100 个文件到一个已有 1GB 文本的库，意味着每次导入都重哈希 1GB。
- `writeEntry`/`writeCsvPatch` 每次写前 `textDocumentBytes` 重走全库算配额（src/bases.ts:225, 260）。

建议：为每个库维护一份轻量 manifest（`<baseId>/.manifest.json`：文件相对路径 → { size, mtime, sha256 }），三类操作增量维护；或退一步，`existingHashes` 只在 manifest 缺失/损坏时全量重建。mtime+size 快路径 + 摘要慢路径是标准做法。

### 4.2 `runRg` 无超时、无输出上限 ✅ 已修复

已落地：`SEARCH_RG_TIMEOUT_MS = 20s` spawn 超时、`--max-count 200`、`--max-filesize 20M`、stdout 超 2MB 即 kill 并带 warning 返回（src/search.ts:147-179, 188-196；常量见 identity.ts:24-27）。

src/search.ts:133-146 把 rg 全部 stdout 缓冲进内存，且 spawn 没有 timeout。大库 + 高频词（如单字「的」）可能产生巨量 match 行。建议：加 `--max-count`/`--max-filesize`、stdout 超过阈值即 kill 并带 warning 返回、spawn 加超时（与 `signal` 联动以便取消）。

### 4.3 `JobRunner.failed` 无界增长 ✅ 已修复

已落地：push 后 `if (failed.length > 20) failed.shift()`（src/jobs.ts:27）。

`failed.push` 只在 `status()` 里 `slice(-20)`（src/jobs.ts:22-27, 37），数组本身无限增长。长期运行的 Host 进程会缓慢泄漏。改为 push 后 `if (failed.length > 20) failed.shift()` 即可。

### 4.4 `markUsed` 每次搜索写盘 ✅ 已修复

已落地：`MARK_USED_THROTTLE_MS = 60_000` 节流，同一 baseId 60 秒内不重复写盘（src/bases.ts:161-173；identity.ts:23）。

每次 `kb_search` 都更新 `lastUsedAt` 并整文件重写 catalog（配合 §3.1 的竞争问题）。建议节流（如同一 baseId 60 秒内不重复写），或把 `lastUsed` 移入 §4.1 的 manifest。

## 8. 补充：结构性优化（第二轮评审）

> 本节是第二轮针对「组织方式」而非「行为」的结构分析。已用 madge 验证：68 个文件无循环依赖。分层本身是干净的：入口（index/commands/tools/private-rpc）→ 编排（ui-operations）→ 领域（bases/ingest/search/catalog）→ 平台（paths/jobs/content）。

### 8.1 依赖方向：基本健康，一处错位 ❌ 未改

复核：仍无 `src/errors.ts`/`src/contract.ts`，`KbError`/`KbErrorCode` 仍在 `types.ts`，叶子模块仍反向依赖它。

`src/types.ts` 名义上是「应用层类型」，实际被 `content/` 叶子模块反向依赖（11 处 import `KbError` / `ReadEntryResult`），同时自己又 import `content/api.ts`——它是事实上的 **shared kernel**，却放在依赖图顶端的位置。建议拆成：

- `src/errors.ts`：`KbError` + `KbErrorCode`（叶子模块只依赖它）
- `src/contract.ts`：领域 DTO，或统一并入 `content/api.ts`

名字与位置匹配真实角色，`types.ts` 退役或只留 Host 内部类型。

### 8.2 引入 `BaseContext` 聚合 ✅ 已修复（与 §3.1 合并落地）

已落地：`withCatalogTx(dataRoot, work)` + `CatalogContext = { dataRoot, catalog }`（src/catalog.ts:114-124），读一次、锁住、执行、按需写回；并发互斥、原子写均挂靠于此。

所有领域函数都是 `(dataRoot, baseId, ...)` 签名，导致一次操作里 catalog 被反复读：

- `writeEntry` = `requireBase`（读 catalog）+ 配额（读 catalog）+ 写（src/bases.ts:218-234）
- `searchBase` = `requireBase` + `markUsed` 两次落盘（src/search.ts:194, 207）

这不是性能小问题，而是结构问题——**没有「单一事务边界」的挂靠点**，§3.1 的并发竞争修不干净。建议：

```ts
type BaseContext = { dataRoot: string; baseId: string; catalog: Catalog }

// withCatalogTx(dataRoot, baseId, fn)：读一次、锁住、执行 fn、写一次
```

并发写互斥、原子写、配额计算、§4.1 manifest 缓存都自然落在这一个函数里。建议与 §3.1 的 P0 修复合并成一次改动。

### 8.3 格式能力声明式化 ❌ 未改（同 §3.3，跟 xlsx 排期）

现在 `readCsvEditorPage` / `writeCsvPatch` 挂在通用 handler 上，registry 用 `format !== EntryFormat.Csv` 特判（src/content/host-registry.ts:83-96），`canEdit` 也是手写标志位。改成能力对象：

```ts
type EntryFormatHandler = {
  format: EntryFormat
  entryExtensions: readonly string[]
  readPreview / readForSearch: ...
  capabilities?: { tableEditor?: { readPage: ...; writePatch: ... } }   // 能力即数据
}
```

效果：registry 里的守卫 if 消失；返回给 Client 的 `EntryCapabilities.canEdit` 从同一来源推导，不再两处维护；将来 xlsx 表格编辑自动获得同一条链路（与 §3.3 合并实施）。

### 8.4 CSV 校验逻辑搬回 csv 模块 ✅ 已修复

已落地：新建 `content/csv/server/patch-schema.ts`——`parseCsvEntryPatch`（RPC 边界收窄）+ `assertCsvPatchShape`（shape 规则单份）；ui-operations 只留一行调用，`editor.validatePatch` 复用 shape 后只剩 revision 对比 + 行列越界（src/content/csv/server/editor.ts:52-57）。

`ui-operations.ts` 里的 `requireCsvPatch` / `requireCsvHeaderChanges` / `requireCsvValue`（src/ui-operations.ts:72-117，约 45 行）是格式专属知识，住在通用 RPC 分发器里，违背了[格式路由方案](./2026-09-03-01-dsh-格式路由重构简版.md)「同一种格式的规则放在一起」的原则。建议搬进 `content/csv/server/`（如 `patch-schema.ts`），ui-operations 只留一行调用。注意：RPC 字段名（`revision`、`headerChanges`、`cellChanges`）是持久契约，只搬实现不改字段。

搬完还有第二刀：`editor.ts` 的 `validatePatch` 又写了一遍 revision 正则、最大修改数、单元格字节上限。三层职责应保持：

- Client `buildPatch`：只组 shape，不校验（已正确）
- RPC `requireCsvPatch`：边界收窄（搬回 csv 模块后仍要留在 Host 边界）
- `editor.validatePatch`：对照已解析文档做行列越界

shape 规则只保留一份，供 RPC 与 editor 共用；editor 只留必须对着文档才能做的越界检查。不要为了「防御纵深」再复制常量和文案。

### 8.5 ingest 参数装配三处重复 ✅ 已修复

已落地：`buildIngestInput` 收进 src/ingest.ts:14，tools/commands/ui-operations 三处均改用。

`src/tools.ts:130`、`src/ui-operations.ts:212`、`src/commands.ts:47` 各自拼 `IngestInput`。抽 `buildIngestInput(raw): IngestInput` 放进 ingest.ts，三处收敛。

### 8.6 不建议动的

- `content/csv/server/csv-document.ts`：标准的纯函数核心（parse / serialize / window 分离，零 IO），保持；
- `client/models.ts` 薄别名层 + `host-payload.ts` 手写运行时校验：刻意的零依赖方案，DTO 增多前不值得引入 zod；
- `executeKnowledgeOperation` 的 op 字符串分发：RPC 持久契约，保持开关形式，只需按 §8.4 移走格式校验；
- 不为两个格式上插件框架；`tableEditor` 能力对象可以做，但是轻量收敛，不是新的格式运行时；
- 不抽通用「分页电子表格编辑器」，等 xlsx 真来了再看共用面；
- 不拆 `styles.ts` 的单 CSS 字符串；CSV 类名已按 `zy-csv-*` 对齐，项目约定如此。

### 8.7 结构项优先级

1. §8.2 `BaseContext`（与 §3.1 P0 合并为一次改动）
2. §8.4 CSV 校验归位 + shape 规则只留一份（可先于 §8.3 做，无 RPC 字段变化）
3. §9.1–§9.4 CSV 编辑链路小收口
4. §8.3 能力声明式化（与 §3.3 合并，跟 XLSX 排期；Client 四处一并收）
5. §8.1 `types.ts` 拆分（顺手做，改动面小但涉及 import 面广；判别联合见 §5.1）
6. §8.5 ingest 装配收敛

## 9. 补充：CSV 编辑链路（第三轮）

> 本节补第一、二轮没写到的 CSV 预览/编辑结构债。不改 §1–§8 的仓库级结论；只把「表格编辑」这条链收完整。`op: 'readCsvPage'` / `writeCsvPatch` 字段名保持不动。

### 9.1 两条写协议，revision 只约束其中一条 ✅ 已决策（方案 3）

已落地：`kb_ingest` 描述已修正为「CSV 可在知源中表格编辑」（src/tools.ts:99）；`op: write` 明确保留为「无条件整表替换」（供命令行与测试），设置页编辑走 `writeCsvPatch` + revision，语义已在本节决策记录写死。

CSV 现在有两条写路径，语义不一致：

| 路径 | 谁在用 | 语义 |
| --- | --- | --- |
| `op: write` → `writeCsvEntry` | 命令 / 测试 | 整文件替换，**不校验 revision** |
| `op: writeCsvPatch` → `writeCsvEditorPatch` | 设置页 UI | 稀疏 patch + revision |

`writeCsvDocument` 被两条路径共用，落盘（BOM、规范化、原子 rename、配额）没问题。缺口在产品层：通用 `write` 对 CSV 仍开放，命令或并发调用可以绕过版本检查整表覆盖。需要先定语义，再改代码：

1. 命令行整表替换也带 revision；或
2. CSV 拒绝 `op: write`，只允许 patch；或
3. 明确保留 `write` 为「无条件整表替换」，并在设计里写死，避免以后被当成漏洞。

决策时还有一个现有佐证：`kb_ingest` 工具描述写的是「CSV 导入后只读」（src/tools.ts:99），而 CSV 实际已通过编辑器可写。若选方案 2，与工具描述的产品语义一致；若选方案 3，应顺手修正 `kb_ingest` 描述，避免「只读」与可编辑并存误导模型。

未决策前不要默默关掉 `write`：`test/csv.test.ts` 和 `test/commands.test.ts` 都覆盖了这条路径。

> **决策记录（2026-09-04）**：采用方案 3——`op: write` 保留为「无条件整表替换」，供命令行与测试使用，不校验 revision；设置页表格编辑一律走 `op: writeCsvPatch` + revision 并发检查。`kb_ingest` 描述已同步修正为「CSV 可在知源中表格编辑」。此语义在此写死，后续不当作漏洞处理。

### 9.2 打开编辑和翻页是两套 API、同一份页 ⚠️ 部分完成

复核：`preview.ts` 的 edit 分支已复用 `readCsvDocument` + `createCsvEditorPage`，与 `readCsvEditorPage` 共享同一实现，「两套 API 各读一遍文档」的重复已消除；未采用「内部转调 `readCsvEditorPage`」的字面形式（保留约 15 行 `csvEditPreview` 组装，因需补 `windowStartLine`/`text`/`totalChars` 等 `ReadEntryResult` 字段）。

树里打开：`read` + `readMode=edit` → `readCsvPreview` 再调 `createCsvEditorPage`  
翻页：`readCsvPage` → `readCsvEditorPage` → 同一个 `createCsvEditorPage`

`preview.ts` 的 edit 分支几乎是 `readCsvEditorPage` 的特化。收口方案采用「Host 内部转调」：通用 `read` 只服务只读 / 命中预览，Host 在 `readMode=edit` 时内部转调 `readCsvEditorPage`，Client 不改、现有「一次 `read` 打开弹框」的 UX 保留。（不走「树打开改调 `readCsvPage(startRow=1)`」那条路，那需要改 Client，收益相同。）这是 API 收口，不是重构。
