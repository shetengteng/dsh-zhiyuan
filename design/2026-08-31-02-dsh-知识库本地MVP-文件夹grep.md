# 个人本地知识库 MVP：原文在文件夹里，用多种关键词 grep

> 修正：不必把正文塞进 SQLite。个人第一版的搜索就是人查资料的那套——先选定知识库，再换几种说法去 grep。SQLite FTS 是篇数多了、需要「哪段更相关」时才换上的目录。  
> 对外用语：知识库 / 类目（子文件夹）。界面与 Skill 不写开柜、落柜。

---

> **两件不同的事，不要绑在一起**  
> 「多种描述查询」是提问策略：把问题扩成几个关键词，一次搜完。SQLite 是可选的检索目录：提前建好「哪个词在哪一页」，用来加速和排序。个人量级，前者贡献大部分命中质量；后者可以后做。

| | |
|--|--|
| **文件夹** | 原文和类目都在这里，不进数据库 |
| **grep** | 在已导入的知识库里按字查找 |
| **一次换词** | 3～8 个说法一起搜，禁止连搜三十轮 |
| **SQLite** | 第一版可以没有 |

---

## 知识存在哪：文件，不是数据库

导入只是把选定的 md/txt 拷进「这个知识库」的目录树。类目 = 子文件夹。查询时 ripgrep 只扫当前这个知识库。

### 插件数据目录（MVP）

```text
~/dsh/data/dsh-knowledge/
├── bases/work/contracts/供应商.md     工作库 · 合同类目 · 原文
├── bases/work/meetings/2024-03.md     工作库 · 会议类目 · 原文
├── bases/life/                        生活库；查工作时这个目录根本不打开
└── catalog.json                       可选：库名、上次用哪个、大约多少篇
                                       （没有也能靠扫文件夹）
```

| | | |
|--|--|--|
| **① 原文** | MVP | 明确导入后拷到 `bases/<库>/<类目>/`。这是唯一的知识正文。AI 读到的片段都从这里来。 |
| **② 登记** | 可很薄 | 文件夹本身就是登记簿：有哪些库、哪些类目、哪些文件。需要进度或去重时，再加一个小 json 记指纹和失败项。 |
| **③ 检索目录** | 后做 | MVP 没有单独目录：每次当场 grep。上千篇或要排序时，再为这个知识库建 SQLite FTS，不改工具名。 |

---

## 查询：先选择知识库，再一次多种关键词

和人查资料一样。差别只有：必须先限定在已导入的知识库里，并且换词只做一轮、一次搜完，不要让 AI 对着全盘循环 grep。

| 步 | 做什么 | |
|----|--------|--|
| 0 | **选库** | 哪个知识库。没说就用最近那个。不是当前代码项目，是已导入的 `bases/` 目录。 |
| 1 | **选类目** | 问题里的「合同」对上子文件夹名，就只 grep 那一层。对不上就在本库全部子文件夹里搜。 |
| 2 | **换多种说法** | 一次给出 3～8 个词：中文、英文、缩写、术语表里的别名。不要第二轮再换。 |
| 3 | **一次 grep** | 在已选目录里用多个关键词 OR 查找，截取命中行附近的段落，打散同一篇，留下 8～20 段。 |
| 4 | **AI 写答案** | 只读这些段，带 `[n]`。没命中就不能说「根据知识库」。项目里的 grep 不算知识库检索。 |

### 走一遍：多种描述怎么变成一次 grep

问：「去年那个供应商合同的违约条款写了什么？」

选定知识库（并可收窄到合同类目）：`bases/work/contracts/`。换词一次：`违约`、`解约`、`termination`、`违约金`、`条款`。

等价于人在终端里：

```bash
rg -n -C 8 -e 违约 -e 解约 -e termination -e 违约金 bases/work/contracts
```

插件把命中收成几段带文件名和行号，交给当前对话模型写答案。会议纪要那个文件夹全程不扫。

> **换词放在一次 kb_search 里，不要让模型连调多次**  
> 工具参数建议带 aliases（3～8 个）。当前对话模型先想几种说法，再调一次 `kb_search`。插件内部一次性 grep。调研里写过：AI 对着仓库反复换词再找，会又慢又贵还容易漏。

## grep 和 SQLite 各解决什么

| | 文件夹 + grep（MVP） | SQLite FTS（后做） |
|--|----------------------|-------------------|
| 正文放哪 | md/txt 文件里 | 仍然在文件里；库里只放「哪个词在哪」 |
| 人怎么查 | 换几个关键词，在这个文件夹里找 | 一样先换词，但目录已经建好，不用每次扫全文 |
| 结果长什么样 | 找到 / 没找到；谁先列出看 grep 顺序 | 能打分：哪一段更相关 |
| 中文 | 按字就能命中（「违约」是原文里的连续字） | 两个字一组入目录，大库更快 |
| 适合 | 个人、几百到一两千篇 md | 篇数上千、文字到 GB、或明确要排序 |
| 短板 | 大了会慢；换词质量取决于当前模型 | 导入要切段建目录；多一步维护 |

## MVP 技术选型

| 部件 | 用什么 | 不要用 |
|------|--------|--------|
| 运行位置 | DSH 插件主进程；搜索走打包好的 ripgrep（和内核查代码同一类工具） | 网页自己扫文件；让 AI 对整个项目 grep 冒充知识库 |
| 原文 + 类目 | `bases/库名/类目/文件.md` | 把全文写入 SQLite；只记路径却从不检查文件还在不在 |
| 查询 | 选库 + 一次 3～8 个关键词 + grep + 截段落 | 模型连搜三十轮；hash 假向量；默认打网上的嵌入接口 |
| 登记 | 文件夹；可选 `catalog.json` 记库名和指纹去重 | 第一版就上 Postgres / 向量库 |
| 文件种类 | md / txt | 第一版承诺 PDF / 扫描件 |

## 给 AI 的工具

| 工具 | MVP | 关键参数 |
|------|-----|----------|
| `kb_list_bases` | 列出 `bases/` 下有哪些知识库、子类目、大约多少篇 | 无；用来先选库 |
| `kb_ingest` | 把本机路径拷进 `bases/<库>/<相对文件夹>/` | `baseId` + 路径；相同指纹跳过 |
| `kb_search` | 只在该库（可选某几个类目）里一次 grep | `baseId`、`query`、`aliases[]`、`category` 可选、`topK` 默认 12 上限 20 |

## 硬规则（仍然要守）

| 规则 | 为什么 |
|------|--------|
| 必须显式导入，不能对当前代码项目直接 grep 就算知识库 | 项目查找是读代码；知识库要能回答「库里有什么」，卸载能清 |
| 查询必须先指定知识库，禁止默认扫全部 `bases/` | 分而治之从第一天就成立，否则以后无法换档 |
| 换词只做一次，合并进同一次 grep | 反复查找又慢又漏；和调研 07 一致 |
| 没命中不得说「根据知识库」；命中必须带文件和片段 | 出处是产品，不是搜索引擎的附赠 |
| 断网时：grep 原文仍能工作；自动换词取决于有没有本地模型 | 和「知识库离线 / 聊天模型离线」那两句拆法一致 |

| | |
|--|--|
| **约 2000 篇** | grep 开始明显变慢时，考虑换 FTS |
| **5 MB** | 单文件上限（md/txt） |
| **10 GB** | 单库文字硬顶，超过拒绝导入 |

## 以后怎么长

| 阶段 | 存放 | 查询 | 何时换 |
|------|------|------|--------|
| 现在 · 个人 MVP | 文件夹即知识库，原文是 md | 选库 → 选类目 → 一次多种关键词 grep | 搜变慢，或需要「哪段更相关」 |
| 下一档 · 本机目录 | 原文仍在文件夹；另建 SQLite FTS | 漏斗不变，grep 换成按字目录；换词保留 | 换说法仍经常漏，且有本机模型时再加语义 |
| 再以后 · 云 | 大文件仓库 + 专业目录 | 同一套 `kb_search`，后面按库/时间分片 | 原文到 TB，或要多人权限 |

> 对照 `design/2026-08-30-05`（项目 grep 不是知识库）、07（换一次词；小库可以先不做目录）、31-01（大了才必须有检索目录）。
