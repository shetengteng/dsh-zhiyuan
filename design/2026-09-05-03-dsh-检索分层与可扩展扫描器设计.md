## 1. 背景与问题

当前检索功能已经支持文件分组、命中统计、全局分页、`path` 单文件分页和 Markdown/CSV 两种内容适配。但代码和结果结构仍然把几种职责放在一起：

1. `search.ts` 同时负责入口分流、关键词处理、路径校验、扫描编排、命中合并和分页。
2. `search-rg.ts` 的实现名称绑定了 ripgrep，未来增加 SQLite、远程检索或其他扫描方式时需要继续修改搜索主流程。
3. 当前结果主要是一个通用的 `SearchResult`，第一层文件概览和第二层文件命中详情的字段语义不完全相同。
4. `render-search.ts` 负责 AI 文本输出，但 Client Card 实际由 `src/client/toolview/KbSearchView.tsx` 负责，两个展示层的边界不够明确。
5. 当前 Card 组件同时处理结果收窄、概览、文件组、命中项和预览选择，后续实现两层结果时会继续变大。

本设计把检索按用户操作拆成两层：

```text
关键词或正则查询
  → 第一层：文件概览（有哪些文件、每个文件多少条、文件列表分页）
  → 选择/指定文件
  → 第二层：文件详情（该文件的命中内容、单文件分页）
```

## 1.1 设计范围与 DSH 工具边界

本文只设计知源的**知识库领域检索层**，不接管 DSH 已有的工作区级文件探索能力。

```text
当前 workdir 的通用探索
  ├─ DSH 原生 glob：发现工作区文件
  ├─ DSH 原生 grep：搜索工作区文本
  └─ DSH 原生 read：读取工作区文件内容或范围

知源知识库检索
  ├─ kb_list_bases：选择已存在的知识库
  ├─ kb_search（无 path）：返回知识库文件概览
  ├─ kb_search（有 path）：返回知识库单文件详情
  └─ kb_ingest：导入并持久化知识库内容
```

边界规则：

1. 用户询问当前项目、当前目录、源码或工作区文件时，使用 DSH 原生 `glob`、`grep`、`read`；这类行为不属于本插件的实现范围。
2. 用户询问已导入资料、知识库、类目或知识库来源时，先使用 `kb_list_bases` 获取真实 `baseId`，再使用 `kb_search`。
3. 本插件不注册与 DSH 原生工具重复的 `glob`、`grep`、`read`，也不通过 DSH 原生工具实现 `kb_search`。
4. `src/search/scanner/ripgrep-scanner.ts` 是 Host 内部的知识库扫描器，不是 DSH `grep` 的封装。即使底层都使用 ripgrep，两者的根目录、输入校验、结果语义和数据所有权仍然独立。
5. DSH 原生 `read` 只负责工作区文件读取，不能替代知识库详情中的 Markdown/CSV 格式适配、引用预览、来源指纹和知识库分页。
6. 不允许 `kb_search` 因为缺少或猜不到 `baseId` 而自动扫描当前工作区，也不允许通过 DSH 原生工具绕过知识库的类目和路径边界。

典型调用流程：

```text
工作区探索：glob（可选） → grep → read
知识库检索：kb_list_bases → kb_search overview → kb_search file-detail
```

本文后续的 `Scanner`、结果 DTO、游标和 Client Card 均指知源知识库检索层；DSH 原生工具的运行时契约由 DSH 提供，不在本文重复设计。

## 2. 设计目标与非目标

### 2.1 目标

1. `src/search/index.ts` 作为搜索领域唯一入口，负责根据是否传入 `path` 分流。
2. 第一层专注文件分布：文件路径、命中数、总数和文件列表分页。
3. 第二层专注单文件命中：文件路径、命中详情、excerpt 和单文件分页。
4. 两层结果使用独立的结果封装和明确的判别字段，不再使用一个扁平结构表达所有场景。
5. 扫描器通过契约接入，当前使用 ripgrep，未来可以增加 SQLite 或远程扫描器。
6. Host 结果封装、AI 文本模板和 Client Card 分离。
7. Client Card 使用独立的 TSX 文件：
   - `src/client/search/SearchOverviewCard.tsx`
   - `src/client/search/SearchFileDetailCard.tsx`
8. 单文件详情查询继续只扫描目标文件，不因为 `path` 查询而扫描整个搜索目录。

### 2.2 非目标

1. 本次设计不引入向量检索或语义检索。
2. 不把 React、JSX 或 Client 私有状态放入 `src/search/`。
3. 不让浏览器直接读取文件或运行 ripgrep。
4. 不为每个小函数创建独立文件；文件按领域职责拆分。
5. 不为旧调用方保留字段、结果形状或游标协议；本设计允许一次性替换 `kb_search` 的输入 schema、输出 DTO、分页游标和 Client 消费方式。

## 3. 总体架构

### 3.1 外部工具分层

本设计的外部入口先按用户意图分成两类。左侧是 DSH 默认提供的工作区探索，不进入知源 Host；右侧才进入本文后续描述的知识库检索管线。

```text
用户查询
   │
   ├── 工作区级问题
   │      ├── DSH glob
   │      ├── DSH grep
   │      └── DSH read
   │
   └── 知识库级问题
          ├── kb_list_bases
          └── kb_search
                ├── overview
                └── file-detail
```

### 3.2 知源内部知识库检索管线

```text
kb_search / /kb search / 设置工作台试搜
                    │
                    ▼
          src/search/index.ts
          搜索入口与模式分流
             │              │
             │ 无 path       │ 有 path
             ▼              ▼
  overview-search.ts   file-search.ts
  文件概览查询          文件详情查询
             │              │
             └──────┬───────┘
                    ▼
          scanner/index.ts
          Scanner 统一契约
                    │
                    ▼
        scanner/ripgrep-scanner.ts
        当前默认扫描器
                    │
                    ▼
       原始命中 path / line / column
                    │
       ┌────────────┴────────────┐
       ▼                         ▼
result/overview-result.ts  result/file-detail-result.ts
第一层结果封装              第二层结果封装
       │                         │
       ├─ AI 文本模板             ├─ AI 文本模板
       └─ presentation 元数据    └─ presentation 元数据
                    │
                    ▼
      Client 搜索结果 Card（TSX）
```

搜索扫描器只返回原始命中位置；文件分组、excerpt、分页、结果封装和 Card 展示由上层负责。

## 5. 搜索入口与两层查询

### 5.1 `src/search/index.ts`

`index.ts` 是搜索目录的公共入口，不承载扫描和展示实现。它负责：

1. 校验基础入参。
2. 解析 `category` 和相对 `path`。
3. 校验并解码自包含分页游标，必要时从游标恢复查询条件。
4. 根据是否有 `path` 分流到第一层或第二层。
5. 按新的 `SearchRequest` / `SearchResult` 契约返回结果；工具 schema、Host DTO、presentation metadata 和 Client 在同一轮切换。

逻辑上等价于：

```ts
export async function searchBase(input: SearchInput): Promise<SearchResult> {
  if (input.path) return searchFile(input);
  return searchOverview(input);
}
```

外部仍然使用一次 `kb_search`：

```text
没有 path：文件概览模式
有 path：文件详情模式
```

### 5.2 第一层：`overview-search.ts`

输入：

```text
baseId + query + aliases + category + limit + files cursor
```

职责：

1. 调用 Scanner 获取当前搜索范围内的原始命中。
2. 按文件分组并统计每个文件的原始命中数。
3. 按确定性规则排序：命中数降序，同数按路径字典序。
4. 按文件数量或结果体积返回文件概览页。
5. 返回 `totalFiles`、`totalHits`、文件摘要和文件列表游标。
6. 不默认生成所有文件的 excerpt。

第一层的核心结果是：

```text
有哪些文件
每个文件命中了多少条
总共有多少个文件和命中
还有哪些文件没有展示
下一页文件列表在哪里
```

### 5.3 第二层：`file-search.ts`

输入：

```text
baseId + query + aliases + category + path + limit + hits cursor
```

职责：

1. 校验 `path` 位于当前搜索根内。
2. 校验符号链接不能逃出知识库。
3. 目标是文件而不是目录。
4. 把规范化的相对路径传给 Scanner，使 ripgrep 只扫描该文件。
5. 读取目标文件的 `SearchDocument`，生成 excerpt 和预览所需字段。
6. 按字符预算分页返回该文件的命中。
7. 返回单文件的 `totalHits`、命中详情和文件游标。

第二层的核心结果是：

```text
当前文件是什么
这个文件一共命中多少条
本页有哪些命中和上下文
该文件还有没有下一页
```

## 6. Scanner 可扩展设计

### 6.1 Scanner 目录职责

`src/search/scanner/` 只处理“如何发现原始命中”，不处理文件概览和 Card 展示。

```text
scanner/index.ts
  统一出口、默认实现选择

scanner/scanner-contract.ts
  Scanner 输入、输出和接口

scanner/ripgrep-scanner.ts
  ripgrep 子进程、argv、JSON 解析、超时和截断
```

### 6.2 Scanner 契约

目标契约可以抽象为：

```ts
export type ScannerInput = {
  rootDir: string;
  /** 已通过 Host 校验的 ripgrep 正则表达式。 */
  terms: string[];
  targetPath?: string;
};

export type ScannerMatch = {
  path: string;
  line: number;
  columnByte: number;
};

export type ScannerResult = {
  matches: ScannerMatch[];
  warnings: string[];
  complete: boolean;
  stopReason?: SearchScanStopReason;
};

export interface SearchScanner {
  scan(input: ScannerInput): Promise<ScannerResult>;
}
```

`ScannerMatch` 定义为 ripgrep 的一个匹配事件：默认对应一条匹配的物理行，而不是该行内每个 submatch 的出现次数。多个正则或多个 submatch 命中同一行时，结果计数只增加一次，`columnByte` 指向该事件的第一个 submatch；CSV 展示层再把物理行映射为逻辑记录。`totalHits`、全局编号和分页位置都遵循这个匹配事件单位。

约束：

1. `targetPath` 必须是搜索层完成 containment 和符号链接校验后的规范化相对路径。
2. Scanner 不接受未经校验的用户绝对路径。
3. Scanner 不读取 excerpt，不解析 CSV 记录，不生成全局命中编号。
4. `complete=false` 时，上层必须把计数当作下限处理。
5. Scanner 更换时，第一层和第二层结果结构不变。

### 6.3 当前 ripgrep 实现

`ripgrep-scanner.ts` 保留现有能力：

```text
--json
--column
--glob-case-insensitive
--max-count
--max-filesize
--glob <content registry globs>
-e <term>
```

全库模式：

```text
rg ... -- .
```

单文件模式：

```text
rg ... -- path/to/file.md
```

`--glob-case-insensitive` 只影响内容扩展名 glob；正则本身保持大小写敏感，除非未来明确增加独立的产品级开关。

未来可以增加：

```text
scanner/sqlite-scanner.ts
scanner/remote-scanner.ts
```

它们只需要实现 `SearchScanner`，不需要修改两层结果封装和 Client Card。

## 7. 结果封装

### 7.1 结果类型

搜索结果使用判别字段，且只保留新的领域结果结构：

```ts
export type SearchResult = SearchOverviewResult | SearchFileDetailResult;
```

两种结果都明确携带 `baseId`、查询条件、分页状态和扫描状态；概览结果不包含命中正文，详情结果只包含一个目标文件的命中正文。不存在 legacy 平面结果或兼容适配层。

### 7.2 公共分页与扫描状态

`result/result-shared.ts` 负责公共结构：

```ts
export type SearchPageInfo =
  | {
      scope: "files";
      returnedFiles: number;
      hasMore: boolean;
      nextCursor?: string;
    }
  | {
      scope: "hits";
      returnedHits: number;
      hasMore: boolean;
      nextCursor?: string;
    };

export type SearchOverviewPage = Extract<SearchPageInfo, { scope: "files" }>;
export type SearchFileDetailPage = Extract<SearchPageInfo, { scope: "hits" }>;

export type SearchScanStopReason =
  | "timeout"
  | "stdout-limit"
  | "per-file-match-limit"
  | "file-size-limit"
  | "io-error";

export type SearchScanInfo = {
  complete: boolean;
  warnings: string[];
  stopReason?: SearchScanStopReason;
};
```

`scope` 必须进入游标 payload，避免文件列表游标和文件命中游标互相混用；`query` 和 `position` 共同描述续页所需的查询条件与位置。`complete=false` 时，所有计数都是下限，文件排序也只能视为当前已发现命中的排序；`page.hasMore` 只表示在当前扫描结果中还有可继续返回的项目，不表示扫描被截断的命中可以通过同一个游标继续获取。

### 7.3 第一层结果：`overview-result.ts`

```ts
export type SearchQuery = {
  /** 已规范化、去重后的 ripgrep 正则表达式。 */
  terms: string[];
  aliases: string[];
};

export type SearchFileSummary = {
  path: string;
  format: "markdown" | "csv";
  totalHits: number;
};

export type SearchOverviewResult = {
  kind: "overview";
  scope: "files";
  baseId: string;
  category?: string;
  query: SearchQuery;
  files: SearchFileSummary[];
  totalFiles: number;
  totalHits: number;
  page: SearchOverviewPage;
  scan: SearchScanInfo;
  presentation: {
    template: "search-overview-card";
    version: 1;
  };
};
```

`scan.complete=false` 时，`totalFiles` 和 `totalHits` 只能解释为当前扫描范围内已发现的下限；模板必须明确显示这一状态。

### 7.5 模板与结果数据分离

`result/templates/` 中的模板是 `.ts`，负责：

1. 生成给 AI 的文本。
2. 生成稳定的 presentation metadata。
3. 将 `complete`、`hasMore`、计数下限等状态转换成人话。

模板不返回 JSX，不读取文件，也不调用 Scanner。

## 8. Client Card 设计

## 8.5 两层检索后的预览状态与交互

对应的视觉原型见 [`2026-09-05-02-dsh-检索结果卡原型.html`](./2026-09-05-02-dsh-检索结果卡原型.html)。原型不再模拟“一个结果卡内嵌多个文件的全部命中”，而是把 overview、file-detail 和右侧预览拆成可以验证数据边界的状态。

### 8.5.1 状态机

Client 只保存当前结果、当前选中文件和当前选中命中的短暂展示态；知识库内容、文件存在性和查询结果仍由 Host 负责。

```text
overview-idle
    │ Host 返回 overview
    ▼
overview-loaded ──点击文件──▶ file-detail-loading
    │                                  │
    │                                  ├─成功──▶ file-detail-loaded / preview-closed
    │                                  └─失败──▶ preview-error
    │
    └─断开连接──▶ disconnected

file-detail-loaded / preview-closed
    │ 点击命中
    ▼
preview-open ──关闭/Escape──▶ file-detail-loaded / preview-closed
    │
    └─切换命中──▶ preview-open（同一右栏原地更新）
```

状态和展示规则：

| 状态                                    | 中间结果区                     | DSH details 右栏                   |
| --------------------------------------- | ------------------------------ | ---------------------------------- |
| `overview-idle`                         | loading、空结果或错误          | 不打开；概览没有命中正文           |
| `overview-loaded`                       | 文件摘要、命中数、文件分页     | 显示“先查看文件详情”，不能直接预览 |
| `file-detail-loading`                   | pending，不显示伪造的命中      | 保持空态，不把 pending 当成已落盘  |
| `file-detail-loaded` / `preview-closed` | 单文件 path、命中和命中分页    | 关闭；等待选择命中                 |
| `preview-open`                          | 保留当前 file-detail           | 显示选中命中的只读 Markdown/CSV    |
| `preview-error`                         | 显示可重试错误，保留已知上下文 | 显示错误或断连，不读取本地文件     |
| `disconnected`                          | 显示连接中断和重试入口         | 不继续使用过期正文冒充当前结果     |

### 8.5.2 overview 到 file-detail 必须经过 Host

overview 文件行的“查看文件详情”不是本地链接，也不是把文件路径交给浏览器读取。`SearchOverviewCard` 只发出业务动作，`KbSearchView` 将动作接到 Host：

```ts
type OpenFileDetailAction = {
  baseId: string;
  query: string;
  aliases?: string[];
  category?: string;
  path: string;
  limit?: number;
};
```

Host 重新校验 `baseId`、`category`、`path` 和查询条件，执行新的 file-detail 查询并返回 `SearchFileDetailResult` 或明确错误。Client 在 Host 确认前只能显示 `file-detail-loading`，不能先把 overview 的 `totalHits` 或文件名当作详情内容。

overview 不包含 `hits`、excerpt 或预览正文，因此 overview 状态没有命中级预览入口。只有 file-detail 返回后，Client 才可以展示当前文件的命中列表；这也保证文件列表分页和单文件命中分页不会互相混用。

### 8.5.3 `path` 是知识库根目录下的相对路径

`path` 的正式语义是：**相对于选定知识库根目录的 POSIX 风格相对文件路径**。例如：

```text
aa/bb/cc.md
```

因此它必须满足：

1. 不以 `/` 开头，不是 macOS、Linux 或 Windows 的绝对路径；统一使用 `/` 作为传输分隔符。
2. 不包含可穿越目录边界的 `.`、`..` 或等价编码；Host 先规范化，再执行知识库根目录 containment、符号链接逃逸和文件类型校验。
3. `path` 不是当前 workdir 的路径，也不是本机绝对路径；不能交给浏览器、Client 或 DSH 原生 `read` 自行解析。
4. 即使 `category` 把搜索范围缩小到某个子树，`path` 仍以知识库根目录为基准。例如类目目录为 `aa` 时，文件仍传 `aa/bb/cc.md`，而不是传 `bb/cc.md`。
5. `SearchFileSummary.path`、`SearchFileDetailResult.path`、`SearchHit.path`、详情游标中的 `query.path` 和预览 payload 中的 `path` 使用同一语义，不能在层间改成不同根目录。

路径只作为 Host 领域对象的相对标识和 Client 的展示文本。Client 可以显示 `aa/bb/cc.md`，但不能根据它拼接本地文件 URL、调用文件系统 API 或执行读取。

### 8.5.4 右侧预览载荷

选中 file-detail 中的一条命中后，`PreviewController` 接收 Host 已返回或由 Host action 返回的结构化预览信息，再调用当前 DSH 版本的 `details` takeover。右栏不改变 DSH 的座椅契约；长期若 DSH 提供 additive preview slot，再移除 takeover。

```ts
type SearchPreviewPayload = {
  baseId: string;
  category?: string;
  path: string; // 知识库根目录相对路径，例如 aa/bb/cc.md
  format: "markdown" | "csv";
  startLine: number;
  endLine: number;
  matchLine: number;
  matchColumnByte: number;
  sourceFingerprint: string;
  previewStatus: "ready" | "loading" | "error" | "stale";
  truncation: "none" | "context" | "content";
};
```

右栏至少展示：

- 文件的知识库相对 `path`、格式和命中序号；不展示绝对路径。
- `startLine`、`endLine`、`matchLine`，并在 Markdown/CSV 内容中定位和高亮命中行。
- `sourceFingerprint`、`previewStatus` 和 `truncation`，使内容过期、上下文截断或 Host 失败可被区分。
- Markdown 使用只读渲染器，CSV 使用只读表格；不提供保存、写文件或编辑命令。

点击另一条命中只更新当前 `PreviewController` 的选择，不在对话中追加消息。关闭按钮、Escape 或 DSH details 关闭动作只关闭右栏，保留当前 file-detail。窗口不足以保留 details 时，窄窗口 Modal 复用同一 payload，不能退化为 Client 本地读文件。

## 9. 自包含游标设计

本设计直接采用 v3 游标作为唯一分页协议，不保留当前 v2 `queryKey` 游标。游标自包含继续查询所需的知识库、查询条件、作用域和分页位置；Host 不保存分页快照。

### 9.1 游标 payload

两层查询使用不同的 `scope`，并使用不同的位置字段：

```ts
type SearchCursorQuery = {
  baseId: string;
  /** 规范化、去重后的 ripgrep 正则表达式。 */
  terms: string[];
  aliases?: string[];
  category?: string;
};

type SearchCursorPayload =
  | {
      version: 3;
      scope: "files";
      query: SearchCursorQuery;
      position: { fileIndex: number };
    }
  | {
      version: 3;
      scope: "hits";
      query: SearchCursorQuery & { path: string };
      position: { hitIndex: number };
    };
```

`terms` 是规范化后的 ripgrep 正则表达式，多个 term 以 OR 关系参与扫描；默认使用 ripgrep 的 Rust regex 语法，大小写敏感，不提供 PCRE2、动态 flags 或 DSH `grep` 的其他通用参数。`query` 必须包含所有会影响结果顺序或内容的条件。`rootDir` 不放进游标，由 Host 根据 `baseId` 重新解析，避免暴露本机绝对路径。

文件概览游标示例：

```json
{
  "version": 3,
  "scope": "files",
  "query": {
    "baseId": "kb-demo",
    "terms": ["供应商"],
    "aliases": []
  },
  "position": {
    "fileIndex": 2
  }
}
```

文件详情游标示例：

```json
{
  "version": 3,
  "scope": "hits",
  "query": {
    "baseId": "kb-demo",
    "terms": ["供应商"],
    "aliases": [],
    "path": "供应商台账.csv"
  },
  "position": {
    "hitIndex": 1
  }
}
```

`position` 是下一页的起始位置，使用从 0 开始的索引。概览页只推进文件索引，详情页只推进当前文件的命中索引。`limit` 是本次返回数量，不需要写入游标；它可以在下一页请求中调整，而不影响起始位置。

### 9.2 编码与续页

对整个 payload 做一次 JSON + Base64URL 编码：

```ts
const nextCursor = Buffer.from(JSON.stringify(payload), "utf8").toString(
  "base64url",
);
```

Base64URL 只是传输编码，不是加密。解码后的游标可以恢复：

```text
scope    → 选择文件概览或文件详情查询
query    → 恢复本次查询条件
position → 确定下一页起始位置
```

调用方式为：

```text
首次查询：kb_search({ baseId, query, aliases?, category?, path?, limit? })
续页查询：kb_search({ cursor, limit? })
```

续页请求只接受 `cursor` 和可选的 `limit`，Host 从游标恢复完整查询条件；调用方不能在续页时修改 `baseId`、`query`、`category` 或 `path`。`limit` 可以调整，但不参与游标身份。

### 9.3 校验和取舍

游标中的 `query`、`baseId` 和 `path` 都是外部输入，不能直接信任。Host 仍需：

1. 校验 payload 版本、`scope` 和位置字段类型。
2. 校验 `baseId` 是否存在，并从 Host 配置重新取得知识库根目录。
3. 对 `path` 重新执行相对路径、containment、符号链接和文件类型校验。
4. 拒绝跨 scope 使用游标，例如把 `files` 游标传给文件详情查询。
5. 将游标长度限制为固定上限（建议 4096 字符），超出则返回明确错误，不无限放大外部 token。

自包含游标不依赖服务端分页状态，也不需要 `queryKey`；代价是游标更长，并且会暴露查询词和相对文件路径。当前设计接受这个取舍。

游标仍然是无状态的。内容变化造成的边界漂移继续由 `sourceFingerprint` 和现有预览失效保护处理。

## 10. `kb_search` 工具契约

`kb_search` 是知源唯一的知识库领域检索工具。它不承担当前 workdir 的通用文件搜索，也不复用 DSH 原生 `glob/grep/read` 的输入或输出契约。

### 10.1 请求

首次查询：

```ts
type InitialSearchRequest = {
  baseId: string;
  query: string;
  aliases?: string[];
  category?: string;
  path?: string;
  limit?: number;
};
```

续页查询：

```ts
type ContinueSearchRequest = {
  cursor: string;
  limit?: number;
};
```

规则：

1. 首次查询必须提供真实存在的 `baseId` 和非空 `query`。
2. `query` 和 `aliases` 都是 ripgrep 正则表达式，多个 pattern 以 OR 关系搜索；默认使用 ripgrep 的 Rust regex 语法，按物理行匹配、大小写敏感，不启用 multiline、PCRE2 或动态 regex flags。`aliases` 表示额外的正则 alternatives，不保证是字面同义词。
3. Host 必须限制 aliases 数量、单个 pattern 长度和全部 pattern 总长度；空 pattern、无法编译的正则和超限输入返回 `invalid_field`，不能启动扫描进程。
4. 正则通过参数数组传给 ripgrep，禁止拼接 shell 命令；错误信息只说明 pattern 无效或超限，不返回子进程堆栈。
5. 未提供 `category` 时搜索整个知识库；提供但不存在时返回明确的 `not_found`，禁止静默回退到知识库根目录。
6. `path` 只接受知识库内相对文件路径，存在 `path` 时进入 `file-detail` 模式。
7. `limit` 在 overview 模式表示本页文件数，在 file-detail 模式表示本页命中数；默认 20、最大 100，必须是正整数，超出范围返回 `invalid_field`，并同时受 Host 字符预算限制。
8. 续页只接受 `cursor` 和 `limit`，不允许附带或覆盖 `baseId`、`query`、`category`、`path`。
9. `baseId`、`category`、`path` 和游标位置都在 Host 边界重新校验。

### 10.2 响应

工具只返回新的判别联合结果：

```ts
type SearchResult = SearchOverviewResult | SearchFileDetailResult;
```

overview 响应：

```text
kind: overview
scope: files
baseId
category
query
files: 文件摘要，不包含 hits
page: 文件分页
scan: 扫描完整性和 warnings
presentation: overview card 元数据
```

file-detail 响应：

```text
kind: file-detail
scope: hits
baseId
category
query
path
format
totalHits
hits: 当前文件命中详情
page: 命中分页
scan: 扫描完整性和 warnings
presentation: detail card 元数据
```

不返回旧的 `files[*].hits` 平面结构，不创建 legacy adapter，不同时维护两套 DTO。工具 schema、Host 结果、AI 模板和 Client Card 必须一次性切换到上述结果类型。

### 10.3 工具与 Client 连接

`tools.ts` 只负责注册新的请求 schema、调用 `search/index.ts` 和声明新的结果 schema；不再把内部结果映射成旧字段。

`render-search.ts` 或拆分后的结果模板直接消费 `SearchResult` 判别联合。`presentationMeta` 至少包含 `kind`、`scope`、分页状态和扫描状态，`KbSearchView.tsx` 直接根据 `kind` 分发到两个 Card。

DSH 原生 `glob/grep/read` 不经过 `tools.ts`，也不进入 `kb_search` 的执行链路。

## 13. 验收标准

### 13.1 第一层概览

- 输入关键词或正则后，可以看到命中文件列表和每个文件的命中数。
- 200 个文件时可以分页遍历文件摘要，不需要一次返回 20,000 条命中正文。
- `totalFiles`、`totalHits`、`complete` 语义明确。
- 文件列表游标不能用于文件详情查询。

### 13.2 第二层详情

- 传入 `path` 后只扫描目标文件。
- 可以看到该文件的命中总数、行号和 excerpt。
- 单文件可以独立分页，详情游标不影响其他文件。
- 目标文件超过扫描上限时明确显示结果不完整。

### 13.3 Scanner 扩展

- ripgrep scanner 的替换不会修改两层结果 DTO。
- 新增 SQLite scanner 只实现 Scanner 契约即可接入。
- Scanner 不返回 JSX、不调用 Client、不负责结果模板。

### 13.4 Client Card

- `SearchOverviewCard.tsx` 只展示文件概览。
- `SearchFileDetailCard.tsx` 只展示单文件命中和预览入口。
- `KbSearchView.tsx` 只做结果识别与分发。
- 覆盖 loading、error、empty、scan incomplete 和正常结果状态。
- Card 不读磁盘、不执行 grep、不模拟持久化状态。

## 13.5 无兼容约束下的实施决策

本设计以一次性切换为前提：当前旧的 `SearchResult`、v2 游标、工具 output schema 和 Client 解析逻辑都视为待删除实现，不为旧调用方保留过渡字段。

1. **类目是硬边界。** `category` 缺失时搜索整个知识库；`category` 不存在时直接返回 `not_found`，禁止静默回退知识库根目录。
2. **查询使用 ripgrep 正则。** `query` 和 `aliases` 先规范化为去重后的正则 pattern，以 OR 关系传给 Scanner；语法采用 ripgrep 默认 Rust regex，按物理行匹配、默认大小写敏感，aliases 只是额外 alternatives，不保证是字面同义词。Host 必须限制 aliases 数量、单 pattern 长度和总 pattern 长度；无效或超限 pattern 返回 `invalid_field`，不能启动扫描进程。
3. **概览和详情完全分离。** overview 只返回文件摘要和文件分页，不包含 `hits`、excerpt 或兼容 preview；需要正文时必须发起带 `path` 的 file-detail 查询。
4. **v3 是唯一游标协议。** 首次请求使用 `baseId/query/...`，续页只使用 `cursor/limit`；不再解析或生成 v2 `queryKey`。
5. **公开 schema 一次性切换。** `tools.ts`、Host 结果 DTO、AI 模板、`presentationMeta`、`KbSearchView` 和两个 Card 同时切换到新的判别联合；不创建 legacy adapter，不保留旧平面字段。
6. **单文件详情保持定向扫描。** Scanner 必须将已完成 containment 和符号链接校验的 `targetPath` 直接传给 ripgrep；`search.ts` 中的二次过滤可以作为防御校验，但不能承担扫描范围控制。
7. **扫描截断和分页截断分开表达。** `limit` 或字符预算造成的分页可以通过 `nextCursor` 继续；ripgrep 的 max-count、max-filesize、stdout 或 timeout 截断只能设置 `scan.complete=false` 并填写 `scan.stopReason`，不能伪造可继续获取的 cursor。单文件超过扫描上限时，详情结果明确是下限，未来若要完整遍历再引入分段扫描或索引。
8. **概览打开详情必须经过 Host。** `SearchOverviewCard` 的 `onOpenFile` 由 `KbSearchView` 接到类型化 Host action，携带 `baseId/query/category/path` 并返回新的 file-detail 结果；Client 不自行调用 DSH 工具、不拼接本地路径。
9. **先测量，再引入索引。** v3 仍然是无状态重扫；只有真实知识库基准证明重复扫描不可接受时，才设计 SQLite、snapshot 或增量索引。
10. **命中单位必须稳定。** `ScannerMatch` 按 ripgrep 匹配事件/物理行计数，不按同一行的 submatch 次数计数；如果未来需要正则出现次数或 CSV 逻辑记录数，必须新增独立统计字段，不能改变现有 `totalHits` 的含义。

### 本文不负责的升级问题

DSH core 升级、profile/bundle 激活、插件命令重新注册和知识库 data root 连续性属于插件安装/运行手册，不属于本搜索管线的 Scanner 或结果 DTO 设计。本文只规定：知源不接管 DSH 原生 `glob/grep/read`，并且 `kb_search` 不依赖 DSH 原生工具的结果契约。

## 14. 当前决策总结

最终采用以下分层：

```text
搜索入口：src/search/index.ts
第一层查询：overview-search.ts
第二层查询：file-search.ts
扫描扩展：src/search/scanner/xxx.ts
结果封装：src/search/result/xxx.ts
AI 模板：src/search/result/templates/*.ts
第一层 Card：src/client/search/SearchOverviewCard.tsx
第二层 Card：src/client/search/SearchFileDetailCard.tsx
```

核心原则：

1. 搜索逻辑和结果封装分离。
2. 文件概览和文件详情使用不同结果类型。
3. 文件列表分页和文件命中分页使用不同游标作用域。
4. Scanner 可替换，当前实现为 ripgrep。
5. Host 使用 `.ts`，Client Card 使用 `.tsx`。
6. `kb_search` 使用新的知识库领域契约，按 `path` 分流 overview/file-detail；不保留旧结果结构或兼容适配。
