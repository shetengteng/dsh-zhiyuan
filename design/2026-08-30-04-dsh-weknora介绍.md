# 社区插件介绍：dsh-weknora（连别人的云知识库）

> 日期：2026-08-30  
> 序号：04  
> 对象：腾讯 WeKnora 官方 DSH 插件 **`@wxg-prc-cpg/dsh-weknora`**  
> 定位：把 **已经跑起来的 WeKnora** 接到 DSH 里的 AI。四个只读工具。插件自己不导入、不改库。  
> 上游：

> - WeKnora 产品：https://github.com/Tencent/WeKnora

---

## 1. 一句话

DSH 内核没有「公司知识库」：项目里查找只看当前仓库，联网搜索只看互联网。这个插件让 AI 去问 **你已经部署好的 WeKnora**：有哪些库、搜原文段落、把一篇读完，或者把整道题交给 WeKnora 自己写答案。

这是社区里最完整的 **「DSH 当遥控器、知识在云上」** 先例。注意两件事：云是 **WeKnora 这份产品**，不是我们以后要自建的那个 API；而且这个插件 **只能读，不能写**。

---

## 2. 在 DSH 里长什么样

标准的主进程插件：注册四个工具。文档强调 **运行时不依赖 DSH 内部的包名**，避免 Harness 改一个字段就装不上。

```text
DSH 里的 AI
    │  列库 / 搜索 / 读一篇 / 整题问答
    ▼
本插件（就是一个 HTTP 客户端）
    │  带上 API 密钥，必要时带上租户编号
    ▼
WeKnora 服务（你自己部署，或公司已经有的实例）
    ├─ 知识库、文档、小段、向量  —— 都在服务端
    ├─ 上传、改、删  —— 走 WeKnora 自己的网页或 API，不走这个插件
    └─ 「整题问答」还会在服务端再调一轮模型
```

上游测过的组合：dsh `0.1.0-rc.8` × WeKnora `0.7.2`。Harness 还在开发预览，作者预期以后会改接口，所以故意不把 DSH 的包版本锁死。

许可证 MIT（和 WeKnora、DSH 一样）。

## 3. 四个工具

| 工具 | 对面的接口（人可以当「去哪问」） | 模型拿到什么 |
|------|----------------------------------|--------------|
| `weknora_list_knowledge_bases` | 列出知识库 | 库名和 id，用来回答「有哪些库」或缩小后面搜索的范围 |
| `weknora_search` | 搜索 | **原文段落**、文档 id、分数、第几段；顺带能对上文件名 |
| `weknora_read_document` | 按篇取小段再拼起来 | 一篇按顺序的正文，带标题和摘要，可以翻页 |
| `weknora_ask` | 开一场 WeKnora 自己的问答 | WeKnora **写好的答案**、引用、服务端用过的工具；可以续同一场 |

上游把分工写得很清楚，我们以后做自己的云客户端应对齐：

- **主力是搜索**：把证据交给 DSH 当前这个模型来写，过程看得见。一次调用既回答「这段话在哪」，也回答「名叫某某的文档在哪」。  
- **读一篇**：搜索只给碎片，命中后要看前后文。每条搜索结果都带着后面读全文需要的 id。第一页先给标题和摘要，避免长文必须翻完才能判断要不要继续。  
- **整题问答要慎用**：等于把题目外包给服务端另一轮模型，适合要跨很多篇综合的题。默认可以等到 5 分钟，回来的是结论，不是你一步步看到的证据。如果配了 WeKnora 自己的 Agent，不要再从插件这边强行改它用哪些库。  
- **没配默认库时**：搜索接口不允许「完全不指定库」。插件会按密钥能看见的库解析一次、记在进程里，搜索和整题问答共用。让模型从一堆难记的库名里猜一个，实际效果更差。

同一套 DSH 配置里可以挂两套 WeKnora（比如内网一套、公网一套），改一下工具名前缀即可。

## 4. 只读：这是和我们「阶段 2 自有云」最大的差别

这个插件 **从不往 WeKnora 里写**：不导入、不改段落、不删除。

| 你想做的事 | 走哪里 |
|------------|--------|
| 列库、搜索、读一篇、让云写答案 | 这个插件的四个工具 |
| 上传文件、从网址导入、手写 Markdown、删文档 | WeKnora 自己的网页或写入接口 |
| 密钥 | 请求头里的 API Key；平台级密钥还要带租户编号 |
| 权限 | 前三个工具有「检索」权限就行；整题问答还要「聊天」权限（会建一场会话） |
| 出错时 | 只回 HTTP 状态和 WeKnora 的原因，**绝不把密钥回给模型** |
| 怕上下文太长 | 进模型前按字数截断（默认大约 1200 字），并标明「被截过」 |

所以：它证明了「DSH 插件 = 云知识库的只读遥控器」这条路通；**它不证明**「在 DSH 里上传到云」已经有官方现成的座位。上传仍然是后端自己的事。

## 5. 安装和配置

```sh
dsh plugin --profile web add @wxg-prc-cpg/dsh-weknora

export WEKNORA_BASE_URL=https://weknora.example.com   # 或本机 http://localhost:8080
export WEKNORA_API_KEY=sk-...
export WEKNORA_KNOWLEDGE_BASE_IDS=kb-123,kb-456        # 可选，默认搜这些库
dsh web
```

也可以在 profile 的配置文件里覆盖整行（覆盖是整份替换，想留的字段必须再写一遍）。地址如果忘了带 `/api/v1`，插件会自己补。没配密钥表示对面是未设鉴权的部署。

配置写错会在 **插件加载时** 就失败，并指出是哪个字段，而不是等到第一次提问才爆。

上游的自动测试值得学：用一次性配置 + 假的 WeKnora + 答案确定的模型，断言 DSH 真的调了工具、答案来自返回值。另外用一份契约文件锁死插件发出的每个请求——我们做云客户端时值得照抄。

## 6. 插件背后那个「云」是 WeKnora 产品

插件只是薄客户端。文件夹树、多种格式导入、段落编辑与回滚、混合检索等，都以你部署的 WeKnora 版本为准。

两条路不要混：

- **如果阶段 2 可以接受「直接部署 WeKnora」**：DSH 侧几乎不用自研搜索，装这个插件就能问；上传和建库走 WeKnora 网页或它的写入接口；产品和别人的差别只剩要不要自己的管理页、品牌、计费。云就不是「我们自己的协议」。  
- **如果阶段 2 必须是自己的接口、自己的存储和登录**：这个插件只能当 **遥控器长什么样的参考**，不能拿来当运行时。

## 7. 和我们方案的关系

| 我们想要的 | 这个插件 | 结论 |
|------------|----------|------|
| 阶段 1 资料不离开这台电脑 | 相反：知识在远程 | **不能**当本机离线版 |
| 阶段 2 插件只当 HTTP 客户端 | 正是这个结构 | **工具怎么分可以照抄**：列库 / 搜索 / 读一篇 / 整题问答 |
| 在 DSH 里上传到云 | 插件不做写入 | 写入要么我们自己的导入接口，要么用 WeKnora 原生上传 |
| 密钥 | 配置里的 key 或环境变量 | 自研应优先走 DSH 的凭据槽，少把密钥写进设置明文 |
| 同时连两套 | 改工具名前缀、插两行 | 本机库和云库并存时可以用同一手法（不同前缀，或库上标明「本机 / 云」） |

**建议**：

1. 愿意把云端建成「WeKnora + 本插件」，阶段 2 会轻很多，但那就不是自有协议。  
2. 坚持自有 API：阶段 1 仍用本机引擎（或先试用 dsh-library）；阶段 2 自己做云客户端，工具按这四件套裁（本机不要注册「整题问答」，或注册了就失败并引导先搜索）。  
3. 文档里不要把 WeKnora 和「我们要养的云」混着叫——一个是现成产品，一个是自己的服务。
