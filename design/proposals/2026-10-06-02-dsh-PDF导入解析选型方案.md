# PDF 导入：解析选型与接入方案

> 日期：2026-10-06
> 序号：02（当日第二份；01 为测试目录下的导入进度测试 Case）
> 定位：给知源「PDF 导入」选库、定文本重组策略与接入点。库内正文仍只落 `bases/<id>/` 下可检索文本。
> 对照：[DOCX 方案](./2026-09-01-01-dsh-DOCX转Markdown方案.md)、[MVP 技术设计 §11.2](./2026-09-01-02-dsh-知源MVP技术设计.md)、[04 导入](./2026-08-31-04-dsh-导入落柜与分类.md)。
> 性质：公开 npm / GitHub 二次整理 + 对照本仓库约束；**未对真实 PDF 样张跑过转换，不声称质量验收通过**。
> 修订：2026-10-06 实现档 — 探针实测：unpdf 1.8.1 内含 PDF.js **6.1.200**；Chrome 导出的中文 CID 样张提取正常、无 U+FFFD。外部 cmap 数据改为**第一档不随包携带**（见 §4.3 修订）；产物 worker 为 `lib/convert-pdf-worker.js`（约 2.3 MB）。
> 用户要求：使用成熟的解析库。

## 1. 一句话

检索只吃库里的文本。`.pdf` 不能原样拷进库，必须在 **Host** 的隔离子进程里用 PDF.js 提取文本层、重组成 Markdown，再走现有 ingest。

第一档只做**文本层 PDF**（Word / LaTeX / 网页打印导出的数字版）。扫描件、加密件直接失败并说人话；OCR 不做。

**推荐组合**：`unpdf` 作接入层（内含 Mozilla PDF.js v5.6.205 serverless 构建）+ 自研纯函数行重组。引擎是 Firefox 内置阅读器同款，周下载约 2500 万，Apache-2.0。

---

## 2. 选库前的约束

| 约束 | 对解析器的要求 |
|------|----------------|
| 转换只在 Host | Node 子进程可跑；禁止进 Client（`src/view`） |
| 拔网线仍能导入 | 禁云 OCR、禁 CDN worker、禁联网取字体或 cmap |
| 无 Python / 少原生 | 纯 JS 优先；禁止 Poppler / Tesseract 系统依赖 |
| 中文可用 | 中文 PDF 多用 CID 字体，解析器必须能加载 cmap 数据 |
| 落盘后能被 ripgrep 扫到 | 产物是 `.md`，不留源 `.pdf` |
| 单文件 5 MB、单库 10 GB | 源与产物各过一遍；配额对象是写出后的字节 |
| 许可可分发 | Apache-2.0 / MIT；拒绝 AGPL（mupdf） |
| 模块 ≤300 行 | 新开 `src/formats/pdf/`；解析库只进子进程入口 |

PDF 特有的范围裁剪（第一档）：

- **只做文本层**。扫描件（整页图）没有文字可提，OCR 属于另一档：成本高、离线包大、中文识别质量难保证，本档明确不做。
- **加密 / 需要密码的 PDF 失败**，错误文案引导用户先在本机解密。
- **不推断标题层级**。PDF 没有可靠的大纲语义（Tagged PDF 极少），字号启发式在合同、论文、双栏版式上误判率高，产出的假 `#` 会污染检索与命中卡。第一档只出段落文本；标题推断留作后续增强，需真实样张支撑。
- **不还原表格**。表格降级为逐行文本；表格转 csv 属于后续增强。
- **不抽图**。同 DOCX：图片进不了 grep，base64 容易顶满配额。

## 3. 库调研（2026-10）

Node 生态里「PDF 提取文本」几乎都叠在 Mozilla PDF.js 上。差别是直接用引擎，还是买一层封装。

```
.pdf（文本层：内容流 + 字体 + cmap）
        →  PDF.js getDocument + 逐页 getTextContent
        →  自研行重组（几何行 → 段落）
        →  .md
```

### 3.1 引擎只有一家能用：PDF.js

| 包 | 角色 | 版本 / 许可 | 现状 |
|----|------|-------------|------|
| `pdfjs-dist` | Mozilla 官方 PDF 引擎 | v5.x，Apache-2.0 | 周下载约 2500 万、53k stars、月度发布；Firefox 内置阅读器同款。成熟度无可争议 |
| `mupdf`（wasm） | 另一完整引擎 | AGPL-3.0 / 商业双许可 | 能力强但许可不可接受，且 wasm 体积大。**不装** |
| `pdf2json` / 其他自研解析 | 独立实现 | 各异 | 维护弱、健壮性远不如 PDF.js。**不装** |

### 3.2 接入层：推荐 unpdf

在 esbuild 打包的 fork 子进程里直接跑 `pdfjs-dist` v5 有三处真实摩擦：

1. v5 需要 `Promise.withResolvers`（Node ≥ 22；项目当前目标是 Node 22，但旧机器上的 DSH 运行时未必）。
2. Node 下 PDF.js 的 fake worker 通过 `import.meta.url` 相对路径动态加载 worker 文件，esbuild 打成单文件后路径错位，需要手工拷出 `pdf.worker.mjs` 或垫 banner。
3. 环境检测分支（Node / browser / worker）需要手工指定 legacy 构建。

`unpdf` 恰好解决这三件事：单文件 serverless 构建、**worker 直接内联进主 bundle**、自带 polyfill；MIT、**0 运行时依赖**、约 453 个 dependents、持续维护（2026-08 仍发版）。它不是再造一层语义，只是把 PDF.js 打包成 Node / edge 能直接 import 的形态——这与 DOCX 档不选 `word-to-markdown` 的理由不冲突：那里的包装没有带来新价值，这里的包装解决的是真实运行时问题。

| 包 | 角色 | 版本 / 许可 | 为什么（不）够用 |
|----|------|-------------|------------------|
| `unpdf` | PDF.js 接入层 | 1.8.1，MIT，0 依赖 | 内含 PDF.js v5.6.205 serverless 构建；`getDocumentProxy` 拿完整 `PDFDocumentProxy`，逐页 `getTextContent` 全程可控；`definePDFJSModule` 保留换官方构建的口 |
| `pdf-parse` | 同类包装 | Apache-2.0，约 10 个月未发布 | 内核 PDF.js 版本旧、只回一个整串文本、拿不到逐 item 坐标。存量下载大但主要是老项目。**不装** |
| `pdfjs-serverless` | unpdf 的底座 | 1.3.1，MIT | PDF.js v5.6.205 单文件再分发；直接用它等价于用 unpdf 少一层 API，不重复引两个。**二选一时取 unpdf** |

**结论**：`unpdf` 精确版本写入 `package.json`，提交 lockfile。实现档开工前在 npm 复核版本，并验证其内含 PDF.js 版本与所拷 cmap 数据的兼容性（见 §4.3）。

备选：若 unpdf 的 serverless 构建在某些样张上表现异常，改用 `pdfjs-dist` legacy build + 显式 `workerSrc` 文件拷贝，接入面不变（都发生在 `worker.ts` 一个文件里）。不并列安装。

### 3.3 看过、不装

| 选项 | 本质 | 不选 |
|------|------|------|
| `tesseract.js` / PaddleOCR | 本机 OCR | 包体几十 MB、中文模型另计、质量难保证；OCR 属另一档。云 OCR（Textract / Document AI）违反离线约束，永不做 |
| `marker` / `docling`（管线式 PDF→MD） | Python 生态 | 禁止 Python；无 Node 入口 |
| 多模态模型读页图 | vision fallback | 依赖联网与模型上下文，违反离线导入；成本不可控 |
| `pdfexcavator` / `@talosjs/pdf` 等新包装 | npm 新包 | 周下载三位数、维护未验证，等生态沉淀 |
| Poppler `pdftotext` | C++ 系统依赖 | 禁止本机原生依赖 |

## 4. PDF 转换怎么接

### 4.1 管道

```text
源文件（只读，压缩体积 ≤ maxFileBytes）
  → contentRegistry.prepareImport（按 .pdf 路由）
  → 子进程 fork lib/convert-pdf-worker.js（30s 硬终止）
      unpdf getDocumentProxy（data 传字节，isEvalSupported: false）
      → 逐页 getTextContent（items: str / transform / width / hasEOL）
      → text-layout 纯函数重组：几何行 → 段落 → markdown
  → 1 个 markdown PreparedEntry（与 DOCX 同模型）
```

输出名规则与 DOCX 一致：`a.pdf → a.md`；产物恒为 1 个 `EntryFormat.Markdown` 条目，无 entryHandler。

### 4.2 行重组策略（`text-layout.ts`，本档核心自研面）

PDF 没有行与段落，只有带坐标的字元簇。重组规则保持最简、可单测：

1. **分行**：按页内 items 的 y 坐标聚类（容差取字高比例），同一 y 带内按 x 排序拼接；`item.hasEOL` 作为行尾佐证。
2. **空格**：拉丁字元簇之间若 x 间距超过字宽阈值补一个空格；CJK 字元直接拼接，不补空格（中文补空格是常见劣质输出，验收必查）。
3. **段落**：仅当连续两行满足「下一行行首无缩进、上一行非句末、行间距小于正文行距」才合并；其余一律换行。宁可碎，不可错。
4. **页间**：每页正文之间以一个空行分隔，不写页码标记。页码会污染 grep 与命中卡；「命中行号 → 页码」的映射留作后续增强。
5. **页眉页脚**：第一档不剔除。剔除规则（重复文本聚类）需要多样张验证，先在保真表里如实声明。

重组是纯函数：输入 items 数组，输出 markdown 字符串，无 IO、无解析库依赖，`test/formats/pdf.test.ts` 直接喂 fixture。

### 4.2b CJK 部首归一（实现档新增）

实测发现 Chrome 打印导出的 PDF，ToUnicode 会把部分汉字映射到 **CJK 部首区**（U+2E80–U+2FDF，如「文→⽂」「长→⻓」「入→⼊」），不归一则检索「文档」命不中「⽂档」。对策：

- `formats/pdf/cjk-radicals.ts`：纯数据表，243 项「部首字 → 统一表意字」，逐条转录自 Unicode 官方 `CJKRadicals.txt`（18.0.0）。
- `formats/pdf/radical-normalize.ts`：`normalizeRadicals`，仅在文本命中部首区正则时逐字符替换；无映射的不成字部首（⺀ 等）原样保留；全角字符等区间外内容不受影响。
- worker 在拼完 markdown 后调用一次；NFKC 不够用（简体部首 ⻓、⻅ 无 compatibility decomposition），必须用显式对照表。

### 4.3 中文与 cmap（本档最高风险点 → 实测已过）

中文 PDF 普遍使用 CID 字体，PDF.js 依靠字体表的 **ToUnicode 映射** 或外部 **cmap 二进制**（`bcmap`）把字元映射回 Unicode。2026-10-06 探针实测（Chrome headless 生成的中文 CID 样张）：

- unpdf 1.8.1 内含 PDF.js 6.1.200；中文提取正常、零 U+FFFD、词序正确——现代导出器（Chrome / Word / WPS / LaTeX）的 PDF 都内嵌 ToUnicode，**不依赖外部 cmap 即可正确映射**。
- 因此第一档**不随包携带 cmap 数据**，不引入 `pdfjs-dist` 数据源依赖：省掉约 2 MB 数据文件与版本对齐负担。
- 代价：无 ToUnicode 的老式 CID PDF（约 2005 年前的制作链）会映射失败。兜底是产物里 U+FFFD / 控制字符占比超过 0.5% 时发 warning「部分文字可能无法正确映射」，不静默也不假装成功。
- 若真实样张验证发现该类 PDF 占比不可忽略，再补「构建时拷贝 cmap 目录 + 传 `cMapUrl`」的增强档；接入面不变，只改 worker 内 `getDocumentProxy` 参数与构建脚本。

### 4.4 资源上限

| 项 | 限制 | 说明 |
|----|------|------|
| 源文件 | `maxFileBytes`（偏好单文件上限） | 子进程内 stat 复验，与 DOCX 相同 |
| 页数 | 512 页，超出按 `file_too_large` 失败 | 防页数爆炸；数值实现档可调 |
| 产物 | `maxOutputBytes` = `maxFileBytes`，发送前自检 | fork IPC 无上限，超限不发送大帧 |
| 时限 | 30s 硬终止（父进程 kill） | 复用 `platform/convert-worker`，无新机制 |
| 父进程兜底 | 逐帧复验 + 20 MB 累计 | 现行机制，不变 |

## 5. 安全边界与失败语义

继承 DOCX 方案 §6 全部条款（fork 隔离、禁 shell、帧协议白名单、发送前自检、断连自退、effect 可卸载、错误不回显原文），PDF 特有补充：

- `getDocument` 参数固定为 `{ data, isEvalSupported: false, cMapUrl, cMapPacked: true }`。**禁用 eval 路径**（PDF.js 对字体 / PostScript 解释器有 Function 构造优化，一律关掉）；不开启渲染，不配置 canvas；`standardFontDataUrl` 文本提取不需要，不携带。
- 子进程只接收已校验的源路径、固定 descriptor 与固定选项；文件字节由 worker 自读，不通过 IPC 传大缓冲。
- 加密 PDF：PDF.js 抛 `PasswordException` → 统一转 `KbError` 通用文案「PDF 已加密，请先在本机解密后再导入」，不回显异常原文。
- 扫描件：全部页文本为空 → 失败，文案「未找到可提取的文字，可能是扫描件，知源暂不支持 OCR」。部分页为空 → 成功 + warning「第 N 页等 M 页没有文字层」。
- 病理 PDF（深层递归、巨型字典）：由 30s 硬终止兜底，与 DOCX 同一保证。

## 6. 模块怎么切

```text
src/
├── model/content-contract.ts     # SourceFormat 增加 Pdf: 'pdf'；EntryFormat 不动
├── formats/pdf/
│   ├── pdf-format.ts             # 注册面：sourceHandlers(['.pdf'])；无 entryHandler（产物是 markdown 条目）
│   ├── pdf-request.ts            # PdfConvertRequest + 校验守卫（对齐 docx-request 形态）
│   ├── text-layout.ts            # 纯函数：items → 行 / 段落 markdown；无 IO、不 import 解析库
│   └── worker.ts                 # 子进程入口；仅此处 import unpdf
├── formats/host-registry.ts      # CONTENT_FORMAT_MODULES 增加一个模块，无新 if
└── view/settings/PrefsPage.tsx   # PDF 行去掉 is-off，改为 checked disabled
scripts/build.mjs / package.json  # convert-pdf-worker 独立 entry → lib/convert-pdf-worker.js；
                                  # files 收录该产物；unpdf 精确版本依赖
```

调用方向固定：`service/kb/import → formats/host-registry → formats/pdf/pdf-format → platform/convert-worker → formats/pdf/worker（子进程）→ formats/shared/ingest-output`。import 编排不出现 `if (ext === '.pdf')`，其余模块不 import unpdf。

测试（镜像发现规则）：

- `test/formats/pdf.test.ts`：text-layout 纯函数（分行、CJK 拼接、拉丁空格、段落合并、页间分隔）+ fixture 整档转换快照。
- `test/platform/convert-worker.test.ts` 补 PDF 用例：超时终止、发送前自检。
- `test/service/kb/import.test.ts` 补 pdf + md 混合批次、扫描件失败、加密失败用例。
- 中文 CID 样张、英文样张、双栏样张、扫描样张、加密样张各入 `test/fixtures/`，命名用业务语言。

## 7. 保真（导入成功 ≠ 版式还原）

| 能保 | 弱或丢 | 直接失败 |
|------|--------|----------|
| 文本层正文（含中文 CID 字体） | 标题层级（不推断） | 需要密码的加密件 |
| 单栏阅读顺序、段落分隔 | 多栏 / 双栏顺序（几何行重组会左右串行） | 扫描件（无文字层） |
| 页间分隔 | 表格结构（降级为逐行文本） | 损坏 / 非法字节 |
| 无字体外部访问（离线） | 页眉页脚（混入正文） | 30s 超时 |
| — | 图片、公式（丢弃 / 乱码风险） | — |

多栏串行与页眉页脚是第一档明确接受的局限，写进关于页与 Skill 文案，不在 UI 承诺。

- [ ] 断网：本机 pdf 仍能导入

## 9. 本档不写进代码的

- OCR（本机或云）、扫描件支持
- 标题层级推断、表格转 csv、页码标记、页眉页脚剔除
- PDF 渲染 / 缩略图 / 预览原页
- 库内保留源 `.pdf`
- Client 端解析、自建 HTTP、动态 import 用户指定的解析器
