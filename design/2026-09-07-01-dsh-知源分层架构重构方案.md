## 1. 为什么改成显式分层

09-06 方案的分解是对的，但顶层轴线是混的：`app/`（层）+ `kb/`（功能）+ `content/`（功能）+ `client/`（端），四个目录用了三种切分标准，且把三个层次（领域服务 / 持久化 / 跨域基础设施）塞进同一个 `kb/`。读的人建立不起统一心智模型。

本文改为**一眼可读的分层**：

| 分层角色                    | 顶层目录          | 一句话职责                                             |
| --------------------------- | ----------------- | ------------------------------------------------------ |
| **view（视图层）**          | `src/view/`       | Client UI，独立 bundle，只经 bridge 调 Host            |
| **controller（控制器层）**  | `src/controller/` | 三个外部入口的入站适配：命令 / 工具 / 私有 RPC         |
| **service（服务层）**       | `src/service/`    | 领域实现：`kb/`（知识库）、`search/`（检索）           |
| **platform（基础设施层）**  | `src/platform/`   | 跨域共用：路径安全 / 任务队列 / 宿主定位               |
| **model（模型层）**         | `src/model/`      | 两端共享的 DTO、wire 契约与常量                        |
| content（格式能力层，横切） | `src/content/`    | 见 §4，唯一横跨 Host+View 的能力层，**不并入任何单层** |

三处按你要求特别显眼：

1. **`client/` → `view/`**：视图层名副其实。
2. **`service/` 包一层**：`kb/`、`search/` 收进 `service/` 之下，领域实现集中。
3. **`controller/` 单独暴露**：命令、工具、私有 RPC 三个入口不再藏在泛化的 `app/`，直接以控制器层命名摆在顶层。

## 2. 两产物边界：分层必须尊重的硬约束

分层不能横跨插件的两个物理产物。`scripts/build.mjs` 有两个入口，编译成两个互不共享运行时的 bundle：

| 产物   | 入口                                             | 格式 / 平台   | React                          |
| ------ | ------------------------------------------------ | ------------- | ------------------------------ |
| Host   | `src/index.ts`                                   | ESM / node20  | 无                             |
| Client | `src/client/index.ts` → 改为 `src/view/index.ts` | CJS / browser | external（`require('react')`） |

两个 bundle **只共享 wire 类型，不共享运行时代码**。因此：

- `view/` 只能 `import type` 模型层的类型，不能 import `service/`、`platform/` 的运行时实现。
- `service/`、`controller/`、`platform/` 是 Host 侧，绝不能被 `view/` 运行时依赖。
- 建库、导入、检索、读写只能经 `view/bridge.ts` → 私有 RPC → `controller/` 进入 Host，**Client 不直接碰文件系统**。

**构建改动（唯一入口变更）**：`scripts/build.mjs` 里 Client 入口 `entryPoints: ['src/client/index.ts']` 改为 `['src/view/index.ts']`；Host 入口 `src/index.ts` 不变；`lib/client.js` 的 `window.__ModuleLoader__.load({ id: 'dsh-zhiyuan', factory })` 包装、external 列表、SKILL.md 拷贝路径都不变。`package.json` 的 `exports["./client"]` 仍指向 `lib/client.js`，产物路径不变。

## 4. content/ 为什么不并入 service（重要，别当成遗漏）

`content/` 是**唯一横跨两个 bundle 的能力层**：`content/*/server/` 编译进 Host，`content/*/client/`（`CsvPreview.tsx`、`MarkdownEditor.tsx` 等 React 组件）编译进 View，`content/api.ts` 是两端共享契约。

如果把它塞进 `service/`（Host 服务层），`service/content/csv/client/CsvPreview.tsx` 就成了“服务层里的视图代码”，直接打脸分层语义；如果按 server/client 拆进 `service/` 和 `view/` 两处，又会把一个格式的实现打散，违背 `content/` 现有“**按格式内聚 + 内部 server/client 分层**”这套本仓库最好的样板，且属于大改，与“保持行为”的目标冲突。

因此 `content/` 保持顶层独立，作为横切能力层，紧贴 `model/` 之上。它内部本身就是分层的（server / client / shared），符合全仓一致的“功能优先 + 层次在内”哲学。`host-registry.ts` 继续是格式路由唯一入口。

## 5. 依赖方向规则

允许的依赖（上层可 import 下层，同层慎重，禁止反向）：

```text
controller ──> service ──> platform ──> model
    │            │            │
    │            └──> content ┘（service 用 content registry 做转换与检索）
    └──> content（controller 渲染工具结果时用 content 类型）
    └──> platform（controller 用 jobs 队列、resolveDataRoot）

content ──> model（叶子模块依赖 KbError / DTO）
platform ──> model（可选，仅类型/常量）

view ──(仅 import type)──> model、content/api、content/*/client 契约
view ──> content/*/client（渲染组件，编译进同一 View bundle）
view ⇢（运行时经 bridge 私有 RPC）⇢ controller
```

明确禁止：

- `view/` 运行时 import `service/`、`platform/`、`controller/`、`model/` 的**实现**（只能 `import type`）。
- `service/`、`content/`、`platform/` 反向 import `controller/` 或 `view/`。
- `search/`（service 域）反向依赖 `kb/`；路径安全统一走 `platform/paths.ts`，不复制。
- 展示组件直接读文件系统、递归扫描或本地持久化。
- scanner 引入 React、bridge 或格式展示代码。

**这套分层顺手修掉了 09-06 的一个真实缺陷**：09-06 把 `paths.ts` 放进 `kb/`，而 `search/search-scope.ts`、`search/file-search.ts` 都 import 它，会形成 `search → kb/paths` 的跨域反向依赖。本文把 `paths` 归入 `platform/`，`search` 与 `kb` 都只向下依赖 `platform`，方向干净。`jobs.ts` 同理：其引用方（`index`、`commands`、`tools`、`private-rpc`、`rpc-dispatch`）都是入口/控制器层，归 `platform/` 才是真归属。
